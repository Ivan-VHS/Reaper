# Энциклопедия 66 низкоуровневых языков и технологий системной разработки

**Дата сверки справочных ссылок:** 2026-11-19  
**Назначение:** инженерный каталог для архитектурного выбора, прототипирования и безопасной интеграции.  
**Статус:** исследовательский справочник. Наличие технологии в каталоге не означает, что она используется данным репозиторием или готова к production-внедрению.

## Как читать каталог

В исходном перечне смешаны собственно языки, диалекты, HDL, ассемблеры, текстовые форматы виртуальных машин, JIT-библиотеки и инструменты генерации кода. Ниже сохранены все 66 позиций, но каждому типу присвоена корректная роль:

- **Язык / диалект** — исходный язык с собственной семантикой.
- **DSL / HDL** — предметно-ориентированный язык либо язык описания аппаратуры.
- **ASM / ISA** — ассемблер, инструкция или низкоуровневое представление.
- **VM / формат** — байт-код, текстовое представление или виртуальная машина.
- **Инструментарий** — компиляторный backend, JIT, мета-ассемблер или runtime.

Практическая интеграция выбирается по артефакту и контракту: объектный файл, статическая/динамическая библиотека, сгенерированный C/C++, WebAssembly, SPIR-V/DXIL, Verilog/VHDL либо ограниченная виртуальная машина. Не все позиции имеют C ABI, не все являются самостоятельными языками и не все поддерживают нативный экспорт функций.

Метки зрелости:

- **Практический путь** — есть воспроизводимая интеграционная модель, но всё равно требуется проверка версии и целевой платформы.
- **Нишевый / исследовательский** — применимость зависит от проекта, активности upstream и доступности компилятора.
- **Исторический / ограниченный** — в первую очередь для сопровождения старого кода, экспериментов или исследований.
- **Инструмент / формат** — не следует учитывать как дополнительный язык приложения.

## I. Современные системные языки с ручным и полуавтоматическим управлением памятью

### 1. Odin — язык системной и data-oriented разработки
**Архитектура.** Компилируемый язык с явным контролем памяти, контекстом выполнения, пользовательскими аллокаторами и удобными структурами данных для игровых и вычислительных систем. Язык не следует путать с C-подобным синтаксисом как гарантией полного ABI-совпадения.

**Интеграция.** На границе с C используйте foreign declarations/import для вызова C-библиотек и отдельно документируйте экспортируемые символы. Для хост-проекта собирайте объектные или библиотечные артефакты, если выбранная версия компилятора и платформа это поддерживают. Передавайте POD-структуры, фиксированные целые типы и буферы с явным размером; не передавайте внутренние Odin-типы напрямую.

**Зрелость:** практический нишевый путь; проверять платформы и конкретный механизм экспорта.

### 2. Hare — минималистичный системный язык
**Архитектура.** Язык для системного ПО с собственным компилятором и компоновкой через объектные файлы; его модель ближе к компактному системному инструменту, чем к крупному runtime-фреймворку.

**Интеграция.** Официальный путь смешивания — скомпилировать C и Hare в объектные файлы и связать выбранным линковщиком. Команда сборки Hare может выдавать объектный модуль; зависимости Hare-модуля при внешней линковке перечисляются явно. ABI в целом совместим с C, но не следует считать его тождественным для всех типов: например, некоторые расширенные C-типы не поддерживаются. Не приписывайте Hare атрибут @export без проверки реального синтаксиса версии.

**Зрелость:** практический нишевый путь для систем Unix-подобного мира; проверять целевые платформы.

### 3. C3 — эволюционный системный язык с C ABI
**Архитектура.** Язык с модулями, обобщениями, контрактами и обработкой ошибок, спроектированный как более безопасная и выразительная альтернатива C без отказа от системного ABI.

**Интеграция.** C3 заявляет совместимость с платформенным C ABI: C-функции объявляются через extern, функции C3 экспортируются через @export, а для стабильного имени можно задать явное имя экспорта. Сверяйте layout структур, calling convention, символы и соглашения владения на каждой платформе. C3 можно подключать как отдельную цель сборки и линковать с C/C++-хостом.

**Зрелость:** практический путь; хороший кандидат для изолированного системного модуля, но не автоматическая замена текущего C-кода.

### 4. Austral — язык с линейными типами
**Архитектура.** Система типов предназначена для выражения однократного владения ресурсом и исключения некоторых ошибок жизненного цикла на этапе компиляции.

**Интеграция.** Рассматривайте его как генерацию C-артефактов или отдельный нативный компонент только после проверки реального backend выбранной версии. Сгенерированный C-код должен собираться стандартной системой проекта, а все внешние интерфейсы — иметь C-совместимые типы и тесты. Не объявляйте код математически доказанным только на основании использования линейных типов: доказательства зависят от границ модели и инструментария.

**Зрелость:** нишевый / исследовательский; перед выбором требуется подтверждение состояния компилятора и backend.

### 5. Vale — generational references и безопасные границы FFI
**Архитектура.** Экспериментальная модель памяти использует ссылки с поколениями и пытается снизить накладные расходы по сравнению с некоторыми традиционными моделями владения.

**Интеграция.** Исторически проект предлагал нативную компиляцию и взаимодействие с C. Однако официальный сайт сообщает, что Vale архивирован и больше не развивается; упоминается продолжение идей в Valen. Не добавляйте Vale как новую production-зависимость. Для наследуемого кода зафиксируйте версию, соберите изолированный пример и проверьте FFI на use-after-free, передачу владения и ABI.

**Зрелость:** исторический / архивирован; изучать концепции, а не выбирать как новую зависимость.

### 6. Cone — язык с градуированным управлением памятью
**Архитектура.** Предлагает сочетать несколько стратегий управления памятью и разрабатывать системные компоненты с более явной моделью владения и aliasing.

**Интеграция.** Встраивать можно лишь после фиксации поддерживаемого compiler snapshot, backend и ABI-контракта. Наличие LLVM- или WebAssembly-пути в проекте не гарантирует полноту языка, стабильность API либо готовую библиотечную упаковку. Начинайте с отдельного процесса/модуля и тестового C ABI, не делайте Cone обязательной зависимостью хоста.

**Зрелость:** нишевый; upstream-план указывает на возобновление активности, поэтому состояние нужно сверять по конкретному commit и feature matrix.

### 7. Beef — компилируемый язык с ручным управлением памятью
**Архитектура.** Статически компилируемый язык с синтаксисом, близким к C#, управляемым временем жизни и ориентацией на игры и нативное ПО.

**Интеграция.** Для C-совместимой границы используйте только документированные экспортные атрибуты актуального toolchain (например, CLink там, где он поддерживается) и проверяйте фактическое имя символа в DLL/SO. C++-классы, исключения и runtime-объекты нельзя безоговорочно переносить через C ABI; создавайте тонкую C-обёртку.

**Зрелость:** нишевый; пригодность зависит от платформы и компилятора.

### 8. Nelua — статически типизированный язык с синтаксисом Lua
**Архитектура.** Компилируется через C и ориентирован на системные и высокопроизводительные участки кода при знакомой Lua-подобной поверхности.

**Интеграция.** Генерируйте C как отдельный build artifact, затем компилируйте его обычным компилятором хоста. Для Lua-проекта можно отдельно реализовать модуль Lua C API и проверить правила lua_State, allocator и stack discipline. Не путайте генерацию C с автоматическим экспортом стабильного ABI: интерфейс библиотеки оформляется отдельно.

**Зрелость:** нишевый; полезен как экспериментальный C-generation путь.

### 9. Carp — функциональный диалект Lisp без GC
**Архитектура.** Статическая типизация и анализ владения сочетаются с Lisp-подобным синтаксисом и генерацией C.

**Интеграция.** Используйте Carp как генератор ограниченного C-компонента или DSL; C-файлы компилируйте в составе обычного CMake/Meson/Bazel проекта. Экспортируйте только явно определённые C-функции и проверяйте жизненный цикл объектов на стыке двух систем. Наличие макросов регистрации не заменяет проверку экспортируемой таблицы символов.

**Зрелость:** нишевый / экспериментальный.

### 10. Dale — Lisp-подобный системный язык
**Архитектура.** Исследовательский язык, сочетающий S-выражения, системные конструкции C и компиляционную обработку AST.

**Интеграция.** Если используемый компилятор формирует объектные файлы, включайте их в обычную линковку хоста и фиксируйте точную версию инструмента. Не обещайте поддержку драйверов, платформ или стабильный C ABI без отдельного проверенного примера.

**Зрелость:** исследовательский / ограниченный.

### 11. Kit — язык с компиляцией в C
**Архитектура.** Нишевый игровой язык, в котором высокоуровневые конструкции преобразуются в обычный C-код.

**Интеграция.** Подключайте стадию генерации C к сборке через отдельную команду, сохраняйте generated-файлы в build-каталоге и запускайте GCC/Clang/MSVC как часть штатной сборки. Проверяйте совместимость с выбранным стандартом C и не коммитьте нестабильный сгенерированный output без необходимости.

**Зрелость:** нишевый / экспериментальный.

### 12. Volt — системный язык, вдохновлённый D и C
**Архитектура.** Экспериментальная компилируемая система с ориентацией на простую низкоуровневую разработку.

**Интеграция.** Рассматривайте только после проверки актуальности компилятора, доступного backend и реальной поддержки целевой ОС. При наличии C ABI оформите отдельную библиотеку; иначе используйте объектную линковку с тестовым минимальным API. Не включайте Volt в обязательный toolchain без CI на нужных платформах.

**Зрелость:** ограниченный / экспериментальный.

### 13. Jakt — язык с трансляцией в C++
**Архитектура.** Проектировался как безопасный системный язык для SerenityOS и опирается на генерацию C++.

**Интеграция.** Встраивайте сгенерированные C++ translation units в сборку с зафиксированными версиями компилятора и стандартной библиотеки. Для внешних языков создавайте C-совместимый façade; прямое смешивание ABI C++ допустимо только при едином компиляторе, runtime и согласованной конфигурации ABI.

**Зрелость:** нишевый; проверять полноту платформ и поддерживаемые части языка.

### 14. Lobster — игровой язык с compile-time reference counting
**Архитектура.** Ориентирован на игры и инструменты; использует анализ времени жизни и может генерировать C++ либо исполнять собственный bytecode.

**Интеграция.** Для embedded-варианта фиксируйте конкретный режим: библиотека/runtime, bytecode VM или generated C++. Данные пересекают границу через C API и POD-структуры. Нельзя считать статический подсчёт ссылок универсальной гарантией отсутствия всех ошибок памяти.

**Зрелость:** нишевый; для игрового/графического прототипирования.

## II. Формальная верификация и высокая надёжность

### 15. ATS (Applied Type System)
**Архитектура.** Сочетает программирование с доказательствами, зависимые и линейные типы; подходит для критичных структур данных и алгоритмов.

**Интеграция.** Компилируйте в C и включайте полученные файлы в общий build. Разделяйте доказательства, которые стираются при компиляции, runtime-проверки и предположения на границе FFI. Для C API задавайте явные ownership-функции и тестируйте все внешние входы.

**Зрелость:** специализированный академический путь.

### 16. F* / Low*
**Архитектура.** F* — язык программирования и верификации; Low* — ограниченный низкоуровневый профиль, моделирующий важные особенности C-подобного исполнения.

**Интеграция.** Верифицированные части могут извлекаться через KaRaMeL в C. Интегрируйте полученные исходники вместе с требуемым support/runtime-кодом и сохраните воспроизводимую цепочку доказательства и генерации. Тестируйте не только алгоритм, но также обёртки, память, ошибки и конфигурацию сборки. HACL* и EverCrypt — известные примеры экосистемы, но их безопасность относится к конкретным версиям, алгоритмам и границам.

**Зрелость:** практический путь для криптографии и чувствительных алгоритмов при строгой проверке provenance.

### 17. Cogent — язык для верифицируемых системных компонентов
**Архитектура.** Ограниченный функциональный язык, в котором ограничения на вычисление и владение помогают доказывать соответствие реализации спецификации Isabelle/HOL.

**Интеграция.** Используйте генерацию C и проверенный интерфейс с хост-компонентом. Встраивание в файловую систему или kernel path требует отдельного доказательства платформенной обвязки, а не только внутренней Cogent-функции.

**Зрелость:** академический / специализированный.

### 18. Dafny и неопределённая позиция «Valea»
**Архитектура.** Dafny — язык со спецификациями и верификацией предусловий, постусловий и инвариантов через SMT. Это не низкоуровневый системный язык. Название «Valea» в исходном перечне не подтверждено как отдельный системный язык; не включайте его в toolchain как идентифицированную технологию.

**Интеграция.** Генерируйте код только в backend, который поддерживается выбранным выпуском Dafny. Современная документация перечисляет различные уровни зрелости для C#, Java, JavaScript, Go, Python, Rust и C++; поддержка C++ описана как ограниченная, Rust — как частичная/развивающаяся. Не заявляйте генерацию C или полноценный backend без проверки release-specific документации.

**Зрелость:** практический инструмент спецификации; выходные backend-цели зависят от версии.

### 19. SPARK — формально анализируемое подмножество Ada
**Архитектура.** Ограничивает конструкции Ada, чтобы статически анализировать поток данных, арифметику, контракты и некоторые классы ошибок.

**Интеграция.** GNAT может компилировать код в объектные файлы; экспорт/импорт через C требует корректных соглашений о вызовах, layout и соответствующих pragma/aspect. Доказательство SPARK не распространяется автоматически на C-обвязку, драйвер или аппаратное окружение.

**Зрелость:** практический специализированный путь для регулируемых и критических систем при наличии компетенции Ada/SPARK.

### 20. Cyclone — безопасный диалект C
**Архитектура.** Исторический эксперимент с регионами, указателями с границами и проверками, направленный на предотвращение ряда классов ошибок C.

**Интеграция.** Для сопровождения legacy-кода возможна изолированная трансляция/замена отдельных модулей, но сначала проверьте доступность компилятора и совместимость с ABI. Не считайте Cyclone современной drop-in заменой C.

**Зрелость:** исторический / академический.

### 21. Vault — исследовательский язык протоколов ресурсов
**Архитектура.** Tracked Types моделируют корректный протокол использования ресурсов — например, жизненный цикл дескриптора.

**Интеграция.** Рассматривайте только для исследования legacy-концепций или поддерживаемого внутреннего компилятора. Не добавляйте в современную production-сборку без доступного toolchain, тестов и доказанного interop.

**Зрелость:** исторический / исследовательский.

## III. Высокоуровневые ассемблеры, мета-ассемблеры и генераторы машинного кода

### 22. HLA (High Level Assembly)
**Архитектура.** Структурированный ассемблер, позволяющий смешивать высокоуровневые управляющие конструкции и машинные инструкции, главным образом в экосистеме x86.

**Интеграция.** Цель — объектный файл, который собирается и линкуется с C/C++-хостом. Внешние функции должны следовать фактическому calling convention целевой платформы; проверяйте регистры caller/callee-saved, stack alignment и unwind metadata.

**Зрелость:** нишевый / исторически ориентированный.

### 23. FASM (Flat Assembler)
**Архитектура.** Многопроходный ассемблер с макросистемой и прямым формированием машинных и объектных артефактов.

**Интеграция.** Генерируйте ELF/COFF либо исполняемый артефакт для конкретной архитектуры и связывайте с C/C++-кодом через ABI. Для hand-written routines требуются тесты calling convention, stack alignment, сохранения регистров, unwind и security mitigations.

**Зрелость:** практический нишевый assembler.

### 24. NESHLA — ассемблер MOS 6502
**Архитектура.** Структурированный ассемблер для 6502-класса и ретро-платформ.

**Интеграция.** Используется в ROM/embedded-образах; связь с C-подобным кодом зависит от компилятора и linker format целевой платформы. Это не интеграционный путь для обычной desktop-библиотеки.

**Зрелость:** ретро / ограниченный.

### 25. PeachPy — Python-мета-ассемблер
**Архитектура.** DSL поверх Python для генерации низкоуровневых x86/x86-64 процедур с контролем регистров и инструкций. Это инструмент генерации, а не отдельный универсальный системный язык; авторство и поддержка должны указываться по upstream-проекту, а не приписываться другому автору без источника.

**Интеграция.** На этапе сборки генерируйте объектные файлы/ассемблерные артефакты для конкретной ABI и компонуйте с C/C++. Держите исходный генератор и его версию в репозитории, а generated output — воспроизводимым. Включайте тесты scalar fallback и CPU feature dispatch.

**Зрелость:** нишевый инструмент; проверять актуальность Python и архитектур.

### 26. C-- / Cmm
**Архитектура.** C-- — промежуточный низкоуровневый язык для реализации backend-компиляторов; Cmm — родственная внутренняя форма, используемая в GHC. Не путайте исследовательский C-- с обычным C/C++.

**Интеграция.** Используйте внутри собственной compiler pipeline, если нужен контроль над стеком, calling convention или runtime-примитивами. Внешнее приложение обычно связывается не с «C-- исходником», а с машинным объектом/символом, полученным из конкретной compiler toolchain.

**Зрелость:** compiler-infrastructure / специализированный.

### 27. VASM
**Архитектура.** Переносимый ассемблер с поддержкой нескольких ISA и объектных форматов.

**Интеграция.** Выбирайте assembler target и object format, затем используйте привычный линковщик. Поддерживайте отдельные исходники/сборочные профили на каждую ISA, а не единый бинарник с предположениями о регистрах и инструкциях.

**Зрелость:** практический путь в embedded/retro и cross-assembly сценариях.

### 28. Sphinx C--
**Архитектура.** Исторический C/assembler-гибрид, не связанный с C-- Саймона Пейтон-Джонса.

**Интеграция.** Применяйте только при сопровождении соответствующей старой кодовой базы или исторической платформы. Для нового приложения предпочтительнее поддерживаемый assembler с явным объектным форматом и документированным ABI.

**Зрелость:** исторический / ограниченный.

## IV. Стековые и конкатенативные языки

### 29. Forth и нативные реализации
**Архитектура.** Стек данных, стек возвратов, расширяемый словарь и интерактивная среда; реализации различаются по наличию JIT, компилятора и встроенного runtime.

**Интеграция.** Встраивайте конкретную реализацию как библиотеку либо используйте отдельный interpreter process. Зафиксируйте версию Forth, словарь примитивов, правила памяти, threading model и ABI callbacks. Gforth, VFX Forth и SwiftForth — разные реализации, а не один бинарно совместимый продукт.

**Зрелость:** практический путь в embedded, firmware и специализированной автоматизации.

### 30. Factor
**Архитектура.** Динамический конкатенативный язык со стековой семантикой, библиотекой и оптимизирующим JIT.

**Интеграция.** Используйте alien FFI для обращения к C API; callbacks требуют явного управления временем жизни callable-объектов и потоковым контекстом. Если Factor запускается внутри хоста, включите ограничения по времени, памяти и доступным внешним функциям.

**Зрелость:** нишевый язык с развитой собственной средой.

### 31. ColorForth
**Архитектура.** Экспериментальная ветвь Forth, в которой цвет токена несёт часть синтаксической роли.

**Интеграция.** Ориентирован на специфическую среду и аппаратные проекты. Встраивание требует собственной реализации runtime/порта, поэтому не следует ожидать универсальный C ABI.

**Зрелость:** экспериментальный / аппаратно-специфичный.

### 32. Retro / RetroForth
**Архитектура.** Компактный Forth-диалект, ориентированный на малую виртуальную машину и переносимое исполнение.

**Интеграция.** Реализация VM на C может быть встроена как небольшая интерпретируемая подсистема. Ограничьте словарь, память, шаги исполнения и host imports; маленький runtime сам по себе не создаёт sandbox.

**Зрелость:** нишевый / встраиваемая VM.

### 33. Cog / Fifth
**Архитектура.** Семейство экспериментальных стековых языков, где статическая проверка stack effect пытается находить underflow и несовместимость стековых эффектов до запуска.

**Интеграция.** Если доступный компилятор генерирует C/WASM, используйте отдельную compile step и контрактный набор тестов. До интеграции подтвердите, какой именно проект/репозиторий имеется в виду: названия Cog и Fifth неоднозначны и не обозначают один общий стабильный стандарт.

**Зрелость:** исследовательский / неоднозначная идентификация.

### 34. Urbit Nock / Hoon
**Архитектура.** Nock — минимальное формальное ядро вычисления над деревьями (nouns); Hoon — более выразимый язык/слой, компилируемый к Nock. В Urbit-runtime критичные операции могут иметь нативные jets.

**Интеграция.** Используйте поддерживаемый Urbit runtime и его протокол взаимодействия. Нативные jets должны быть семантически эквивалентны соответствующим Nock-операциям и проходить differential tests; не вызывайте внутренние runtime-функции напрямую без закреплённого интерфейса.

**Зрелость:** специализированная VM-экосистема.

## V. GPU, шейдеры, FPGA и гетерогенные вычисления

### 35. Slang
**Архитектура.** Модульный язык и компилятор для shader/compute-кода с абстракциями, generics, интерфейсами и несколькими backend-целями.

**Интеграция.** Компилируйте через slangc или API в подходящий артефакт — например SPIR-V для Vulkan, DXIL для Direct3D 12, CUDA/PTX, Metal либо другие поддержанные цели конкретного выпуска. Выбор цели должен учитывать runtime и устройство; shader bytecode не подключается как обычная C-библиотека. Верифицируйте capability/profile на целевом GPU.

**Зрелость:** практический путь для графики и GPU compute.

### 36. Halide
**Архитектура.** DSL для вычислительных конвейеров, который разделяет математический алгоритм и schedule — размещение, тайлинг, векторизацию и параллельное исполнение.

**Интеграция.** Генерируйте AOT-библиотеку и заголовок либо используйте JIT API. Подключайте к C/C++ через сгенерированный callable API; измеряйте полную стоимость преобразования данных и передачи на ускоритель, а не только kernel time.

**Зрелость:** практический путь для изображений, видео и массивов.

### 37. Futhark
**Архитектура.** Функциональный язык для параллельной обработки массивов; backend может использовать C и доступные GPU-механизмы в зависимости от сборки.

**Интеграция.** Компилятор формирует C API и runtime для контекста/буферов. Обёртка для Python/Rust/C# должна соблюдать порядок создания/освобождения контекста и владение GPU-памятью. Поддержка конкретного backend определяется версией компилятора и платформой.

**Зрелость:** практический нишевый путь для data-parallel задач.

### 38. Taichi
**Архитектура.** Python-hosted DSL для физики, графики и параллельных вычислений, генерирующий kernels для CPU/GPU targets.

**Интеграция.** Для production host без Python исследуйте AOT export конкретной версии. Встраивайте только документированный AOT artifact и generated API, закрепите target architecture и runtime dependencies. Наличие Python-примера не означает наличие стабильного автономного C API для каждого backend.

**Зрелость:** практический исследовательский инструмент; AOT-совместимость требует проверки.

### 39. Spiral
**Архитектура.** Многостадийный генератор оптимизированных программ для SIMD, DSP и линейной алгебры.

**Интеграция.** Используйте как offline code generator: генерируйте специализированные C/C++/assembly артефакты и компилируйте их тем же pinned toolchain. Сохраняйте параметры специализации, архитектурные требования и проверку корректности против scalar reference.

**Зрелость:** нишевый инструмент генерации высокопроизводительных kernels.

### 40. Bend / HVM
**Архитектура.** Bend — функциональный язык, компилируемый в представление для Higher-Order Virtual Machine. Модель вычислений исследует параллелизм и редукцию графов; конкретный CPU/GPU backend нельзя предполагать по одному названию проекта.

**Интеграция.** Встраивайте через опубликованный runtime API или запуск отдельной задачи. Прежде чем обещать CUDA/GPU путь, проверьте актуальный backend, платформы и ограничения HVM release. Передача крупных данных между хостом и VM должна быть измерена.

**Зрелость:** экспериментальный / быстро меняющийся стек.

### 41. Clash
**Архитектура.** Функциональный HDL на базе Haskell, преобразующий синхронную логику в synthesizable HDL.

**Интеграция.** Выходом являются Verilog/VHDL/SystemVerilog и отчёты синтеза, не обычная библиотека приложения. Связь software-хоста с FPGA-модулем строится через определённый регистровый интерфейс, DMA, PCIe/AXI или другой аппаратный протокол, а затем через драйвер и пользовательский API.

**Зрелость:** практический FPGA-инструмент при наличии соответствующей платы и цепочки синтеза.

### 42. SpinalHDL
**Архитектура.** Scala-based HDL для генерации цифровых схем, тактовых доменов и шин.

**Интеграция.** Генерируйте HDL, проводите lint/simulation/synthesis и тесты на уровне протоколов. Приложение на C/Rust обращается к спроектированному hardware block только через согласованный MMIO/DMA/device API; сам SpinalHDL не является runtime-библиотекой desktop-программы.

**Зрелость:** практический FPGA/SoC путь.

## VI. Исторические и ретро-системные языки

### 43. BCPL
**Архитектура.** Машинно-словная модель данных и ранняя традиция системного программирования; исторический предшественник B и C.

**Интеграция.** Используйте современный BCPL toolchain или Cintcode runtime для сохранения старых программ. Взаимодействие с host API оформляйте через документированные system calls/bridge функции, а не через неподтверждённую прямую ABI-совместимость.

**Зрелость:** исторический, но применимый для эмуляции и наследуемых систем.

### 44. B
**Архитектура.** Ранний бестиповый системный язык Bell Labs, предшественник C.

**Интеграция.** Для современных систем это преимущественно исследовательский/образовательный сценарий: трансляция в ассемблер или C, затем сборка стандартным toolchain. Проверяйте разрядность и историческую семантику машинного слова; не переносите предположения старых платформ на x86-64/ARM.

**Зрелость:** исторический / образовательный.

### 45. BLISS
**Архитектура.** Системный язык, созданный для реализации системного ПО, известный своей семантикой адресов и разыменования.

**Интеграция.** Для OpenVMS и совместимых окружений связывайте объектные модули согласно конкретной ABI и calling convention платформы. Для переноса на Linux/Windows понадобится портирование runtime/API, а не просто включение исходника.

**Зрелость:** legacy / платформа-специфичный.

### 46. PL/M
**Архитектура.** Язык для ранних микропроцессоров Intel, включая 8- и 16-битные семейства, с близостью к аппаратным портам и прерываниям.

**Интеграция.** Сохраняйте старую сборочную цепочку либо переносите алгоритмы через проверенный транслятор/ручную миграцию в C. Любую замену портового I/O, прерываний и layout структур тестируйте на симуляторе и целевом оборудовании.

**Зрелость:** legacy / embedded maintenance.

### 47. Mesa
**Архитектура.** Язык и среда Xerox PARC, известные модульными интерфейсами, исключениями и сопрограммами.

**Интеграция.** Для исторического ПО используйте совместимую VM, эмуляцию или портирующий слой. Утверждение о конкретном переводчике в C должно подтверждаться для выбранного проекта; это не универсальная команда современной toolchain.

**Зрелость:** исторический / исследовательский.

### 48. Modula-2 / Modula-3
**Архитектура.** Модульные языки семейства Вирта; Modula-3 добавляет развитые механизмы типов, исключений и различение безопасного/небезопасного кода.

**Интеграция.** Используйте актуальный компилятор (например GNU Modula-2 или CM3 для подходящего варианта языка). C interop определяется конкретным компилятором, foreign module декларациями, ABI и runtime; Modula-2 и Modula-3 не имеют взаимозаменяемых интерфейсов.

**Зрелость:** нишевый/legacy, но компиляторы доступны.

### 49. Oberon / Oberon-07 / Active Oberon
**Архитектура.** Минималистичное семейство системных языков с модульностью, расширением типов и тесной связью с историческими ОС Oberon/A2.

**Интеграция.** Возможны трансляция в C или отдельный runtime/ОС. Учитывайте диалект и конкретный компилятор; calling convention, object layout и inline assembly различаются. Не объединяйте все варианты Oberon в один гарантированный ABI.

**Зрелость:** нишевый / исторический, полезен для обучения и специализированных систем.

### 50. STOIC
**Архитектура.** Исторический интерактивный стековый язык/компилятор, применявшийся в задачах управления и сбора данных.

**Интеграция.** В современных системах обычно требуется эмулятор или перенос логики на Forth/C. Внешние датчики и лабораторные интерфейсы подключайте через контролируемый host adapter, а не через перенос старых I/O предположений.

**Зрелость:** исторический / исследовательский.

## VII. WebAssembly, eBPF, JIT и специализированные VM

### 51. WebAssembly Text Format (WAT)
**Архитектура.** Человекочитаемое текстовое представление инструкций WebAssembly, а не самостоятельный высокоуровневый язык приложения.

**Интеграция.** WAT преобразуется в WASM-модуль через WABT или другой поддерживаемый toolchain. Хост исполняет бинарный модуль в совместимом runtime (например Wasmtime/Wasmer/WAMR) либо в браузере. Контракт должен определять exports/imports, линейную память, ABI, WASI-профиль, fuel/time budget и лимиты памяти.

**Зрелость:** практический sandbox-формат; безопасность зависит от настроек runtime и host capabilities.

### 52. AssemblyScript
**Архитектура.** Строго типизированный TypeScript-подобный язык, предназначенный для компиляции в WebAssembly через asc/Binaryen.

**Интеграция.** Сборка создаёт .wasm и описание/loader для хост-окружения. Передавайте данные через линейную память и согласованные экспортируемые функции; JavaScript objects не становятся автоматически совместимыми со структурами WASM. Учитывайте memory growth и версию loader.

**Зрелость:** практический веб/WASM путь.

### 53. Grain
**Архитектура.** Функциональный язык, ориентированный на WebAssembly, с pattern matching и алгебраическими типами.

**Интеграция.** Генерируйте WASM и подключайте через поддерживаемый runtime. Проверяйте ABI конкретного Grain release, WASI preview/version, host imports и наличие libc/runtime support, если оно требуется. Не предполагайте, что любой модуль является WASI-командой только потому, что это WASM.

**Зрелость:** нишевый / развивающийся WASM-язык.

### 54. Virgil
**Архитектура.** Компилируемый язык для виртуальных машин, компиляторов и системных компонентов, исследовавший собственные пути генерации машинного кода.

**Интеграция.** Фиксируйте компилятор и целевую платформу; подключение возможно через нативный артефакт либо импортированные host-функции WebAssembly, если они поддерживаются выбранным toolchain. Сверяйте текущее состояние проекта до включения в обязательную сборку.

**Зрелость:** нишевый / исследовательский.

### 55. eBPF / C для eBPF / Aya / BPFtrace
**Архитектура.** eBPF — ограниченная регистровая VM и формат программ для контролируемого исполнения в kernel context; C и Rust/Aya — возможные frontends/toolchains, BPFtrace — язык и инструмент трассировки. Это не одна языковая реализация.

**Интеграция.** C/eBPF обычно компилируется Clang в BPF object, затем загружается через libbpf; Aya предоставляет Rust API. BPFtrace используется для диагностических сценариев. Проверяйте verifier, kernel version, helper/map availability, privileges и ограничения платформы. В desktop-приложении предпочтителен read-only/observability профиль с явным согласием пользователя; не подменяйте eBPF обычным драйвером и не заявляйте, что он поддерживается каждой ОС.

**Зрелость:** практический Linux observability/security инструмент при корректных привилегиях и проверке ядра.

### 56. DynASM
**Архитектура.** Генератор кода/assembler DSL, используемый для встраивания машинных инструкций и построения JIT-компонентов.

**Интеграция.** Обрабатывайте .dasc-файлы отдельным генератором во время сборки, а полученный C включайте в хост. Runtime должен корректно управлять executable memory, W^X, instruction cache flush, relocations и сменой защиты страниц. Не исполняйте произвольные сгенерированные байты без threat model.

**Зрелость:** практический инструмент внутри JIT/toolchain.

### 57. SLJIT
**Архитектура.** Stack-less JIT backend на C, предоставляющий абстрактное низкоуровневое API для генерации кода на нескольких архитектурах.

**Интеграция.** Подключайте как библиотеку/исходный компонент, закрепите release и target ISA. Тестируйте generated-code buffers, executable memory policy, ABI и fallback для архитектур без JIT. Это runtime-компонент, а не язык приложения.

**Зрелость:** практический инструмент для встроенных JIT.

### 58. AsmJit
**Архитектура.** C++ библиотека для эмиссии машинного кода x86/x64 и AArch64, с абстракциями ассемблера и runtime memory management.

**Интеграция.** Подключайте через CMake или пакетный менеджер с закреплённой версией. Используйте отдельные target-specific генераторы; тестируйте ABI, CPU feature dispatch, executable memory и корректный scalar fallback. Исключения C++ и внутренние объекты не должны пересекать C ABI.

**Зрелость:** практический инструмент для эмуляторов, рендеринга и JIT.

## VIII. Экспериментальные, эзотерические и академические технологии

### 59. Janus — обратимый язык
**Архитектура.** Обратимые вычисления проектируют так, чтобы операции имели обратный ход без необратимого уничтожения информации.

**Интеграция.** Используйте симулятор/компилятор для научной модели, обратимых алгоритмов и проверки свойств. Интеграция в C/C++ обычно идёт через generated code или процессный интерфейс. Не выводите из обратимости программы обещание нулевого энергопотребления аппаратуры: реальные схемы, память и ввод-вывод имеют дополнительные затраты.

**Зрелость:** академический / экспериментальный.

### 60. Subleq — OISC / одноинструкционная архитектура
**Архитектура.** Машинная модель с одной инструкцией subtract-and-branch; это архитектура/ISA и соответствующий ассемблерный язык, а не универсальный язык системного программирования.

**Интеграция.** Используйте маленький интерпретатор/эмулятор как учебную VM или тестовую песочницу. Задайте размер памяти, число шагов, проверку адресов и завершение. Для защиты программ не считайте обфускацию Subleq криптографической защитой.

**Зрелость:** учебный / исследовательский.

### 61. Movfuscator — однокомандный компиляторный backend
**Архитектура.** Исследовательская техника преобразования C-кода в последовательности ограниченного набора машинных инструкций (в классическом варианте — MOV-only x86).

**Интеграция.** Рассматривайте как экспериментальный compiler output для анализа/обфускации, а не как новый язык или замену системной toolchain. Сравнивайте бинарную корректность, производительность, совместимость с ABI и инструменты анализа на точной архитектуре.

**Зрелость:** исследовательский инструмент.

### 62. ParaSail
**Архитектура.** Параллельный язык с безопасной моделью разделения данных и параллельного вычисления, ориентированный на устранение ряда типичных гонок.

**Интеграция.** Интеграция возможна через доступный нативный backend и документированные импорт/экспорт интерфейсы. До практического применения проверяйте поддержку платформы, runtime и зрелость компилятора; автоматическое распараллеливание не отменяет измерений и проверки семантики.

**Зрелость:** нишевый / исследовательский.

### 63. Terra
**Архитектура.** Низкоуровневый язык, метапрограммируемый из Lua и связанный с LLVM; позволяет строить и компилировать специализированный код из host-скриптов.

**Интеграция.** Используйте Lua-скрипты для генерации и компиляции Terra функций, затем публикуйте стабильные C ABI entry points или объектные артефакты, если это поддерживает выбранная сборка. Отделите доверенный генератор от недоверенных входных данных.

**Зрелость:** нишевый / исследовательский.

### 64. Koka / Perceus
**Архитектура.** Функциональный язык с algebraic effects и алгоритмом Perceus для точного управления ссылками и повторного использования памяти без обычного tracing GC в соответствующих путях.

**Интеграция.** Используйте документированный C backend и FFI границу, если они доступны в выбранном выпуске. Явно определите lifetime объектов, callbacks, effect handlers и освобождение памяти; не сводите функциональные эффекты к простым C-вызовам без контракта.

**Зрелость:** активный исследовательский язык с потенциально полезным C interop.

### 65. Rigel — аппаратно-ориентированный потоковый DSL
**Архитектура.** DSL для описания потоковых конвейеров обработки изображений/сигналов, ориентированных на FPGA/ASIC и планирование пропускной способности. Это отдельная позиция; повторное упоминание Lobster в исходном перечне было дубликатом пункта 14.

**Интеграция.** Генерируйте аппаратные описания и C++/симуляционную модель, если конкретная реализация это поддерживает. Проверяйте функциональное соответствие модели RTL, latency/throughput, ресурсы FPGA и аппаратные тесты. Хост-программа общается с ускорителем через конкретный driver/API и DMA/MMIO.

**Зрелость:** специализированный FPGA/ASIC research tool.

### 66. ChucK
**Архитектура.** Язык для аудио и интерактивной музыки с сильной моделью времени, в которой события могут быть привязаны к аудио-сэмплам/тактовому времени движка.

**Интеграция.** Встраивайте libchuck либо используйте поддерживаемый game-engine bridge. Объявите частоту дискретизации, размер блока, thread ownership, политику callbacks и бюджет realtime-потока. В realtime audio callback нельзя выполнять блокирующий I/O, аллокации с непредсказуемой задержкой или обычные mutex-wait.

**Зрелость:** практический специализированный audio runtime.

## Универсальные паттерны интеграции

### A. C ABI и нативная линковка
Подходит для языков с подтверждённым платформенным C ABI, объектных файлов и библиотек.

1. Сформируйте маленький стабильный façade: opaque handle, функции create/destroy, операции и явный error code.
2. Используйте фиксированные типы ширины, указатели плюс длину, явно определённое выравнивание и версию ABI.
3. Не передавайте через границу внутренние String/Vec/array/closure/object структуры без документированного binary layout.
4. Память освобождает сторона, которая её выделила, либо библиотека предоставляет парную функцию release.
5. Не допускайте выхода C++/Rust/других исключений/паник через C ABI.
6. Callback-контракт фиксирует поток, повторный вход, время жизни и способ отключения callback.
7. Проверяйте exports, imports и фактический calling convention на Windows x64 и System V AMD64 отдельно; другие архитектуры требуют своей проверки.

### B. Генерация C/C++ как source-to-source
Подходит для ATS, Low*, некоторых functional/system DSL и языков с реальной C/C++-генерацией.

- Запускать генератор как явный build step с pinned version и детерминированными параметрами.
- Размещать output в каталоге сборки, не перезаписывать пользовательские исходники.
- Собирать generated code тем же toolchain, что и host, только если совместимы стандарты, ABI и runtime.
- Сохранять compiler logs и provenance; generated source не является доказательством корректности.
- Добавить тесты на исходный язык, generated output и host wrapper.

### C. WebAssembly / WASI и VM sandbox
Подходит для WAT, AssemblyScript, Grain, Retro-подобных runtime и отдельных модулей.

- Задайте imports/exports, ABI и версию WASI до реализации.
- Включите лимиты памяти, fuel/инструкции, timeout, stack, размер ввода и output.
- Выдавайте capability только для конкретного host function; по умолчанию imports запрещены.
- Сопоставляйте trap, cancellation и runtime failure с типизированной ошибкой приложения.
- Не называйте VM безопасной песочницей без настройки системных ресурсов и аудита host imports.

### D. GPU / FPGA / аппаратные backend
Подходит для Slang, Halide, Futhark, Taichi, Spiral, Clash, SpinalHDL и Rigel.

- Разделяйте control plane, CPU fallback и accelerator kernel.
- Проверяйте устройство, драйвер, runtime, compiler target и точность типов до запуска.
- Учитывайте стоимость подготовки данных, transfer, синхронизации и копирования обратно.
- Сравнивайте с CPU baseline на тех же данных, а не только kernel throughput.
- Для FPGA добавляйте RTL simulation, synthesis reports, timing closure и hardware-in-the-loop tests.
- Не выдавайте генерацию HDL/шейдеров за управление реальным оборудованием без драйвера и устройства.

### E. Assembly и JIT
Для FASM, VASM, HLA, DynASM, SLJIT и AsmJit.

- Документируйте ISA, calling convention, сохранение регистров, stack alignment и unwind.
- Проверяйте CPU feature flags перед dispatch; обязательно сохраняйте portable fallback.
- Управляйте executable memory по W^X-политике, корректно сбрасывайте instruction cache там, где это необходимо.
- Тестируйте на эмуляторе/виртуальной машине и на реальной целевой архитектуре.
- Не загружайте произвольный машинный код из сети и не предоставляйте JIT генератору секреты хоста.

### F. Формальная верификация
Для SPARK, F*, Low*, ATS, Cogent и Dafny.

- Явно указывайте, какое свойство доказывается, какие предположения заданы и какой компонент находится за границами proof.
- Храните спецификацию, toolchain version, proof logs и generated artifact hashes.
- Проверяйте FFI-обвязку, runtime, компиляторные флаги и платформенный код отдельно.
- Используйте differential/property/fuzz tests как дополнительную проверку; тесты не заменяют доказательство, а доказательство не исключает ошибку окружения.

## Минимальный контракт любого внешнего модуля

Каждый модуль, написанный на дополнительном языке или сгенерированный сторонним инструментом, обязан предоставить:

| Поле | Требование |
|---|---|
| Identity | Язык/инструмент, upstream URL, версия, commit/tag |
| Target | OS, архитектура, ABI, compiler target, runtime |
| Artifact | object/library/WASM/shader/HDL/source/VM module |
| API | Версионированный контракт, типы, ошибки, ownership |
| Capabilities | Минимальные разрешённые host imports и системные права |
| Resources | Лимиты времени, памяти, потоков, буферов и очередей |
| Build | Воспроизводимые команды, pinned tools и зависимости |
| License | Лицензии исходников, генератора и runtime |
| Tests | Contract, boundary, fuzz, sanitizer и platform tests |
| Fallback | Поведение при отсутствии toolchain/runtime/hardware |
| Status | proposed / prototyped / integrated / verified / disabled |

## Критерии допуска в репозиторий

1. **Сначала измерить необходимость.** Дополнительный язык нужен для конкретной задачи, которую нельзя адекватно решить текущим стеком.
2. **Не размножать toolchain ради каталога.** Справочник сам по себе не основание добавлять компилятор в обязательную сборку.
3. **Один владелец границы.** Модуль должен иметь ответственного, API, тесты и план удаления/замены.
4. **Сборка по умолчанию остаётся воспроизводимой.** Дополнительные compiler SDK — опциональные build features.
5. **Проверять лицензии и происхождение.** До импорта исходников/генераторов проверить LICENSE, зависимости, версии, integrity и SBOM.
6. **Сравнить стоимость FFI.** Измерять маршалинг, копирование, запуск runtime, переключение контекста и передачу данных.
7. **Никаких недоказанных обещаний.** Не приписывать модулю memory safety, hard realtime, formal verification или ускорение без измеримого подтверждения.

## Уточнения и неоднозначности исходного списка

- **Vale** архивирован; для нового проекта изучать Valen или альтернативы, но не рассчитывать на поддержку Vale.
- **Hare** смешивается с C через объектные файлы и линковку; документация описывает ABI, в целом совместимый с C, но отдельного универсального @export-пути из исходного текста не подтверждает.
- **C3** действительно документирует C ABI, extern, @export и явное имя экспортируемого символа.
- **Dafny** — язык спецификаций/верификации с несколькими backend; это не низкоуровневый системный язык и поддержка backend зависит от версии.
- **«Valea»** не идентифицирован как отдельный язык в проверенных справочных источниках; оставлен как неразрешённая метка исходного текста.
- **PeachPy** — Python-based assembler/code generator; не самостоятельный системный язык.
- **WAT** — текстовая форма WebAssembly, не независимая VM и не обычный native язык.
- **eBPF** — виртуальная ISA/VM и kernel execution environment; BPFtrace, Aya и C frontends — разные слои инструментария.
- **DynASM, SLJIT и AsmJit** — инфраструктура генерации/исполнения кода, а не языки уровня приложения.
- **Movfuscator** — исследовательский compiler/backend; **Subleq** — ISA/OISC; оба включены как близкие низкоуровневые технологии.
- **Rigel** — отдельный аппаратный DSL; повтор Lobster в 65-й позиции исходного текста исправлен.
- **Clash и SpinalHDL** генерируют HDL для аппаратной реализации; они не заменяют обычные desktop/server библиотеки.
- **Bend/HVM, Cone и Taichi AOT** меняются быстро; перед включением в CI сверяйте точный release, backend и supported targets.
- Любое упоминание скорости, полной memory safety или формальной надёжности требует отдельных измерений/доказательств.

## Профиль внедрения: Reaper

### Существующая архитектура, от которой нельзя отходить
В репозитории есть Python reference interpreter и развиваемая нативная C17 implementation line: CMake target reaper_core, CLI, lexer, parser/AST, небольшой проверяемый Canonical IR, checked constant folding и ограниченный AST-to-IR lowering. Документы проекта отдельно фиксируют: IR opcode set и lowering slice неполны; native code generation, полный runtime, ownership/effect analysis и WASM backend ещё не заявлены как завершённые.

### Приоритет интеграции
1. **Сохранить C17 как текущий native implementation target.** Энциклопедия — карта будущих технологий, не основание менять язык реализации или семантику REAPER/MOST.
2. **Сначала завершить типизированный Canonical IR и проверки.** Только после name resolution, type/effect checking и ownership analysis выбирать дополнительный backend.
3. **Первый внешний backend — generated C либо C ABI.** Generated C полезен как проверяемый промежуточный шаг; прямой C3/Odin/Rust модуль допустим только за узким версионированным интерфейсом.
4. **Dafny/SPARK/F*/Low* — для proof/contract work, не как подмена runtime.** Проверять арифметику, IR invariants и ownership assumptions, сохраняя доказательства и границы формальной модели.
5. **WASM/WASI — будущая plugin target.** Она может дать более сильную изоляцию для расширений, но требует отдельного runtime, capability imports, memory/fuel limits и conformance tests. Сейчас наличие архитектурной схемы WASM не означает реализованный backend.
6. **GPU/FPGA и JIT — не ранний этап.** Они допустимы только после появления реального workload, профилировщика и измеримого выигрыша после стоимости передачи данных/FFI.

### Рекомендуемая последовательность
- M0: документировать target matrix и неизменяемый C17 reference contract.
- M1: расширить typed IR, verifier и differential tests.
- M2: определить versioned C ABI/WIT module contract, ownership и effects.
- M3: прототипировать один backend (сначала generated C или WASM), не меняя Python compatibility oracle.
- M4: запускать differential/property/fuzz tests и проверять compiler artifacts.
- M5: только после подтверждения поведения включать backend в поддерживаемые release targets.

### Защитные правила
Не позволять внешнему языку менять семантику оператора ~>, make/vary/change, диагностику или порядок вычислений. Ни одна FFI-функция не получает ambient filesystem/network/process access. Resource budgets интерпретатора не являются sandbox; неподтверждённый native plugin нельзя исполнять как доверенный код. Формальное доказательство для одной функции не сертифицирует весь runtime.
