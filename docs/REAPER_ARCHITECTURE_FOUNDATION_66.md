# Архитектурный фундамент Reaper: 66 понятий

## Назначение

Этот каталог превращает 66 архитектурных терминов в согласованную модель Reaper. Это не 66 независимых подсистем и не набор взаимозаменяемых синонимов. Каждое понятие получает стабильный числовой ID, машинный ключ, английское и русское имя, слой и точное назначение.

Реализация v1 находится в native C17 core:

- include/reaper/architecture.h — публичный API и типы;
- src/architecture.c — неизменяемый каталог, поиск и проверка графа;
- tests/test_architecture.c — conformance-тесты;
- CMakeLists.txt — сборка и регистрация native CTest.

Каталог не подменяет существующие language, IR, runtime, host ABI или hardware-модули. Он задаёт общий словарь и предоставляет ограниченный валидатор архитектурных зависимостей.

## Девять архитектурных слоёв

| Слой | Назначение |
|---|---|
| Structural foundation | Каркас, архитектура, основа, структурные уровни и точки расширения |
| Platform and execution | Целевая платформа, среда выполнения, runtime, engine, kernel и host |
| Toolchain and reusable assets | Библиотеки, пакеты, инструменты, стеки, middleware и адаптеры |
| Design and models | Контекст, модели, паттерны, парадигмы, методология и подход |
| System composition | Система и её декомпозиция на подсистемы, модули, компоненты, блоки и узлы |
| Contracts and specifications | Интерфейсы, протоколы, стандарты, регламенты, спецификации и схемы |
| Topology and boundaries | Матрицы, сетки, контуры и периметры |
| Workspace and reference points | Плацдарм, опорная точка, базовая линия и рабочие области |
| Hardware/software integration | Аппаратно-программная граница и интеграция с доверенным host adapter |

### Полный каталог

1. **Каркас — Framework frame (framework-frame).** Фиксирует главные части и допустимые отношения между ними.
2. **Платформа — Platform (platform).** Целевая ОС, процессор, ABI и заявленные host-сервисы.
3. **Среда — Environment (environment).** Настроенные условия и ресурсы, в которых работает инструмент или программа.
4. **Инфраструктура — Infrastructure (infrastructure).** Общие сервисы, хранилища, сборочные ресурсы и эксплуатационная поддержка.
5. **Архитектура — Architecture (architecture).** Декомпозиция, границы владения и направления зависимостей.
6. **Базис — Basis (basis).** Минимальный согласованный набор примитивов для верхних уровней.
7. **Основа — Base (base).** Стабильная стартовая реализация, общая для зависимых возможностей.
8. **Фундамент — Foundation (foundation).** Инварианты и контракты, обязательные до добавления расширений.
9. **Остов — Skeleton (skeleton).** Минимальная обязательная форма законченной системы.
10. **Костяк — Backbone (backbone).** Ключевые компоненты, сохраняющие основной поток системы.
11. **Структура — Structure (structure).** Явное расположение частей и связи между ними.
12. **Конструкция — Construction (construction).** Конкретная сборка реализаций в работающее целое.
13. **Экосистема — Ecosystem (ecosystem).** Управляемый набор репозиториев, инструментов, пакетов и интеграций вокруг Reaper.
14. **Надстройка — Extension layer (extension-layer).** Верхнеуровневая возможность, расширяющая основу, но не владеющая ею.
15. **Оболочка — Shell (shell).** Пользовательская или интеграционная поверхность над внутренними контрактами.
16. **Рантайм — Runtime (runtime).** Жизненный цикл программы, выполнение и управление ресурсами.
17. **Среда выполнения — Execution environment (execution-environment).** Конкретное состояние процесса, конфигурация, квоты и capabilities одного запуска.
18. **Движок — Engine (engine).** Заменяемый исполнитель: интерпретатор, bytecode VM или native backend.
19. **Ядро — Kernel (kernel).** Минимальная доверенная часть, координирующая критичные ресурсы и базовые сервисы.
20. **Библиотека — Library (library).** Повторно используемый код с вызываемыми и документированными интерфейсами.
21. **Набор инструментов — Toolset (toolset).** Связанный набор инструментов для конкретного рабочего процесса.
22. **Инструментарий — Tooling (tooling).** Компилятор, форматтер, отладчик, тесты и сборочные инструменты с явными входами и выходами.
23. **Тулкит — Toolkit (toolkit).** Интегрированный набор библиотек и инструментов для одной предметной области.
24. **Пакет — Package (package).** Версионируемая единица распространения с объявленными зависимостями.
25. **Стек — Stack (stack).** Упорядоченный набор слоёв, совместимость которого проверяется целиком.
26. **Технологический стек — Technology stack (technology-stack).** Выбранные язык, компилятор, runtime, платформа и технологии интеграции.
27. **Шаблон — Template (template).** Параметризованная исходная модель для создания проектов и модулей.
28. **Скелет — Skeleton template (skeleton-template).** Минимальная раскладка проекта с обязательными файлами и границами.
29. **Бойлерплейт — Boilerplate (boilerplate).** Повторяющийся генерируемый код, который должен оставаться небольшим и проверяемым.
30. **Базовый слой — Base layer (base-layer).** Нижний общий слой ПО, открытый верхним уровням через узкий контракт.
31. **Прослойка — Middle layer (middle-layer).** Ограниченный слой преобразования или координации между отдельными слоями.
32. **Мидлвар — Middleware (middleware).** Компонент обработки запросов или событий между поставщиками и потребителями.
33. **Связующее ПО — Glue software (glue-software).** Адаптеры и оркестрация, соединяющие независимые компоненты без слияния их ответственности.
34. **Контейнер — Container (container).** Ограниченная единица упаковки или изоляции с явными ресурсными и доверенными пределами.
35. **Хост — Host (host).** Процесс или ОС, предоставляющие сервисы через явный host ABI.
36. **Контекст — Context (context).** Ограниченные конфигурация, идентичность, состояние и capabilities операции.
37. **Модель — Model (model).** Формальное представление предметной области, состояния системы или преобразования.
38. **Паттерн — Pattern (pattern).** Повторно используемое решение с известной областью применимости и компромиссами.
39. **Парадигма — Paradigm (paradigm).** Согласованные семантические правила проектирования программ и инструментов.
40. **Концепция — Concept (concept).** Именованная проектная идея с определённой областью и последствиями.
41. **Методология — Methodology (methodology).** Повторяемый процесс планирования, реализации, ревью и сбора доказательств.
42. **Подход — Approach (approach).** Выбранная практическая стратегия решения ограниченной инженерной задачи.
43. **Система — System (system).** Целостная единица с ответственностью, интерфейсами и наблюдаемым поведением.
44. **Подсистема — Subsystem (subsystem).** Отдельно ограниченная часть системы с узким внутренним контрактом.
45. **Модуль — Module (module).** Связная единица с явными экспортами, зависимостями и жизненным циклом.
46. **Компонент — Component (component).** Единица реализации с одной ясно определённой ответственностью.
47. **Блок — Block (block).** Небольшая композиционная единица данных, поведения или преобразования.
48. **Узел — Node (node).** Участник графа с типизированными входящими и исходящими связями.
49. **Интерфейс — Interface (interface).** Публичные операции и форма данных, видимые через границу компонента.
50. **Протокол — Protocol (protocol).** Правила взаимодействия и переходов состояний между участниками.
51. **Стандарт — Standard (standard).** Нормативная цель совместимости с версией и правилами соответствия.
52. **Регламент — Policy (policy).** Обязательное правило управления или эксплуатации с владельцем и точкой контроля.
53. **Спецификация — Specification (specification).** Проверяемое описание поведения, ограничений и отказов.
54. **Схема — Schema (schema).** Машиночитаемая структура данных и контракт её проверки.
55. **Матрица — Matrix (matrix).** Многомерная таблица связей для сравнения покрытия и совместимости.
56. **Сетка — Grid (grid).** Регулярная раскладка для разделения или индексации элементов.
57. **Контур — Boundary (boundary).** Определённая граница, за которой проверяются владение, данные и эффекты.
58. **Периметр — Perimeter (perimeter).** Полная защищаемая область системы, процесса или execution capability.
59. **Рабочая среда — Work environment (work-environment).** Установленные и настроенные инструменты конкретной задачи разработки или эксплуатации.
60. **Рабочая область — Workspace (workspace).** Область проекта для исходников, конфигурации, артефактов и состояния задач.
61. **Плацдарм — Foothold (foothold).** Стабильная точка входа для расширенной интеграции или миграции.
62. **Опорная точка — Anchor point (anchor-point).** Именованная стабильная ссылка: версия ABI, инвариант или граница релиза.
63. **Базовая линия — Baseline (baseline).** Измеренное эталонное состояние для обнаружения регрессий и оценки изменений.
64. **Несущая конструкция — Load-bearing structure (load-bearing-structure).** Критический слой зависимостей, контракты которого должны оставаться стабильными.
65. **Аппаратно-программная база — Hardware/software base (hardware-software-base).** Явная граница hardware, firmware, драйверов и host ABI; привилегированный доступ остаётся у доверенных адаптеров.
66. **Программный каркас — Software framework (software-framework).** Повторно используемая система правил жизненного цикла, extension points и общих сервисов приложений.

## Native API

Заголовок include/reaper/architecture.h публикует:

- каталог: reaper_architecture_concept_count, concept_at, concept_find_by_id, concept_find, concept_find_ru;
- каталог слоёв: reaper_architecture_layer_count, layer_at;
- проверку графа: reaper_architecture_graph_validate;
- детерминированную сортировку зависимостей: reaper_architecture_graph_order;
- имена диагностик: reaper_architecture_status_name.

Строковый поиск по key и русскому имени точный и чувствительный к регистру. Числовые ID 1–66 являются стабильными идентификаторами v1; существующие ID нельзя переиспользовать.

### Модель зависимостей

Ребро { dependent, dependency } означает: dependent требует dependency. Все узлы и обе стороны каждого ребра должны присутствовать в графе. Валидатор отклоняет неизвестные и повторяющиеся узлы, отсутствующие зависимости, self-dependency, повторные рёбра и циклы. Топологическая сортировка возвращает сначала зависимости, затем использующие их узлы; при равной готовности выбирается меньший ID.

Граф ограничен 66 узлами и 512 рёбрами. API не выделяет память, не загружает модули и не исполняет код.

### Пример

~~~c
#include "reaper/architecture.h"

const ReaperArchitectureConceptId concepts[] = {
    REAPER_ARCH_CONCEPT_PLATFORM,
    REAPER_ARCH_CONCEPT_HOST,
    REAPER_ARCH_CONCEPT_RUNTIME
};
const ReaperArchitectureDependency dependencies[] = {
    { REAPER_ARCH_CONCEPT_HOST, REAPER_ARCH_CONCEPT_PLATFORM },
    { REAPER_ARCH_CONCEPT_RUNTIME, REAPER_ARCH_CONCEPT_HOST }
};
ReaperArchitectureGraph graph = {
    concepts, 3U, dependencies, 2U
};
ReaperArchitectureConceptId order[3];
size_t written = 0U;
ReaperArchitectureError error;

if (reaper_architecture_graph_order(&graph, order, 3U, &written, &error)
    != REAPER_ARCHITECTURE_OK) {
    /* Report error.message; do not continue with an invalid architecture. */
}
~~~

## Границы реализации v1

Реализованы каталог из 66 элементов, девять слоёв, точный поиск, проверка архитектурных графов и dependency-first порядок. Это не означает, что все 66 понятий стали отдельными исполняемыми подсистемами. Создание процессов, контейнеризация, управление драйверами, физический MMIO, развёртывание пакетов и запуск приложений остаются ответственностью отдельных runtime/host/hardware контрактов.
