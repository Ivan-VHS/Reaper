# Reaper: адаптация 66 инженерных правил backend/runtime

**Проект:** Ivan-VHS/Reaper  
**Назначение:** обязательное техническое задание для укрепления локального runtime, компилятора, сервисов разработчика и интеграционных адаптеров.  
**Статус:** implementation specification; это не отчёт о завершённой реализации.

## 1. Область применения и архитектурное решение

Reaper — локальный язык системного программирования и Windows Studio. Его основной контур состоит из языка \`.rpr\`, lexer/parser, reference runtime на Python, экспериментального native C17-контура, CLI/REPL, Studio, stdio LSP/DAP, локальных отчётов, системных профилей и внешних toolchain-адаптеров.

Поэтому эти 66 правил применяются к **runtime/backend-слою Reaper**, а не используются как повод добавлять веб-сервер, пользовательские HTTP API, облачные сессии, SQL-базу, CORS, публичные сокеты или кластер. Сетевые и распределённые механизмы внедряются только при появлении конкретного поддерживаемого сценария и отдельного versioned contract.

### Основные контуры ответственности

1. **Language core:** лексер, парсер, AST, семантические проверки, каноническая модель языка.
2. **Compiler core:** типизация, эффекты, HIR/MIR/LIR, верификация IR, lowering, генерация кода и ABI.
3. **Reference runtime:** вычисление программы, области видимости, квоты, ошибки, управление ресурсами и явные host effects.
4. **Native runtime and hardware adapters:** C17, MMIO descriptors, ABI, platform/HAL adapters; физический доступ остаётся за доверенным драйвером/host adapter.
5. **Developer services:** CLI, REPL, LSP, DAP, formatter, diagnostics и toolchain discovery.
6. **Studio and project state:** документы, профили сборки, настройки, отладочные сессии и безопасные файловые операции.
7. **Reports and governance:** JSON schemas, report envelope, local audit, security policy, CI и release evidence.

Python reference runtime остаётся compatibility oracle до тех пор, пока отдельный набор differential/conformance tests не подтвердит эквивалентность native backend для конкретного подмножества языка.

## 2. Правила реализации — 66 требований

### I. Архитектура, границы и контракты (1–12)

1. **Границы доменов.** Разделять language core, compiler, runtime, host adapters, IDE services, Studio и отчётность. Домен не должен напрямую изменять внутреннее состояние другого домена в обход его API.  
   **Приёмка:** зависимости слоёв проверяются тестом/статическим правилом; отсутствуют циклические импорты и доступ к приватному состоянию соседнего слоя.

2. **Строгие входные и выходные схемы.** Явно описать типы, обязательные поля, диапазоны, ограничения длины и версии для JSON-отчётов, project/target profiles, plugin manifests, LSP/DAP payloads, native ABI и межпроцессных сообщений.  
   **Приёмка:** валидные fixtures проходят; отсутствующие, неизвестные, неверно типизированные и чрезмерные поля дают детерминированную ошибку до изменения состояния.

3. **Транспорт отдельно от логики.** CLI, LSP, DAP, Studio и внешние процессы преобразуют данные в вызовы ядра и обратно; бизнес- и языковая семантика не дублируется в обработчиках протоколов.  
   **Приёмка:** одинаковая операция, запущенная из CLI и Studio, использует один сервисный путь и возвращает совместимый результат.

4. **Единый источник истины.** Для каждой сущности определить владельца состояния: открытый документ — document/workspace service; конфигурация проекта — project profile; активная транзакция — transaction owner; семантика — language core; статус возможностей — проверяемый feature registry. Не поддерживать независимые копии одного значения.  
   **Приёмка:** обновление состояния проходит через владельца; кэш помечен как производный и имеет явную стратегию обновления.

5. **Идемпотентность операций.** Повторный запрос на форматирование, проверку, генерацию отчёта, отмену задачи или применение профиля не должен создавать дублирующие побочные эффекты. Для операций записи использовать operation key, ожидаемую версию или атомарную замену файла.  
   **Приёмка:** повтор одинаковой команды не повреждает проект и не создаёт дополнительных артефактов; конфликт версии возвращается явно.

6. **Единая модель ошибок.** Ввести стабильные категории ошибок: input/validation, syntax, semantic, limit, permission/capability, IO, protocol, toolchain, conflict и internal. Сохранять source span, operation context и безопасное сообщение; traceback — только в диагностическом режиме.  
   **Приёмка:** CLI/LSP/DAP отображают предсказуемые коды и контекст; секреты и внутренние данные не попадают в пользовательский ответ.

7. **Версионирование контрактов.** Версионировать report envelope, project manifests, plugin interfaces, IR serialization, language protocol extensions, target profiles и ABI. Несовместимое изменение требует новой версии или явной миграции.  
   **Приёмка:** неизвестная major-версия отклоняется; совместимое расширение не меняет смысл существующих полей.

8. **Правильная модель синхронности.** Чистый анализ, parsing и локальные операции остаются прямыми вызовами. Асинхронность используется для subprocess, длительной сборки, индексирования, отменяемых задач и UI responsiveness, а не вводится без измеримой причины.  
   **Приёмка:** короткие операции не создают фоновые очереди; долгие операции не блокируют UI и могут корректно завершаться/отменяться.

9. **Явные побочные эффекты.** Парсер, type checker и оптимизации не читают произвольные файлы, сеть, окружение и часы. File/process/native effects доступны только через явный adapter/capability и отражены в контракте функции.  
   **Приёмка:** тесты доказывают отсутствие скрытого I/O при syntax/type check; запрещённый effect отклоняется до выполнения.

10. **Малые композиционные модули.** Новые компоненты должны иметь одну ответственность, узкий публичный API и минимум глобального изменяемого состояния. Не создавать универсальный manager, если достаточно конкретного сервиса.  
    **Приёмка:** модуль можно тестировать отдельно через публичный контракт; циклы и необоснованные singleton-состояния отсутствуют.

11. **Конфигурация отдельно от реализации.** Target triple, ABI, memory map, compiler paths, timeouts, limits, feature flags и каталоги кэша задаются профилями/CLI/environment с безопасными значениями по умолчанию. Секреты не сохраняются в исходниках и примерах.  
    **Приёмка:** поведение тестируется на разных профилях без редактирования исходного кода; неизвестные параметры отклоняются или явно помечаются.

12. **Детерминизм.** Одинаковые входные байты, версия компилятора, target profile и явные параметры должны давать одинаковые диагностики и воспроизводимый build output, насколько это допускает toolchain.  
    **Приёмка:** golden и repeat-build tests сравнивают нормализованные отчёты, IR и fingerprints; недетерминированные поля исключены из сравнения документированно.

### II. Данные, хранилища, схемы и транзакции (13–24)

13. **Валидация на границах.** Проверять UTF-8, размеры файлов, source ranges, JSON shape, пути, идентификаторы, адреса и диапазоны чисел при входе, а не после частичной обработки.  
    **Приёмка:** негативные tests покрывают пустые, повреждённые, чрезмерные и граничные значения.

14. **Инварианты данных.** AST, IR, target profile, register descriptors и manifests проверяются отдельными валидаторами. Некорректное состояние нельзя передать следующему этапу компилятора.  
    **Приёмка:** каждый lowering stage имеет positive/negative invariant tests; invalid IR завершается контролируемой ошибкой.

15. **Атомарность связанных изменений.** Изменение профиля и его версии, запись отчёта и metadata, сохранение проекта и индекса должны фиксироваться целиком либо не применяться. Для файлов использовать temp-file + flush/fsync (где поддерживается) + atomic replace.  
    **Приёмка:** fault-injection между стадиями не оставляет частично записанного конечного файла.

16. **Управляемые миграции.** Изменения project settings, target manifests, caches и persisted state оформлять как versioned migrations с проверкой исходной версии, резервной копией и документированным rollback. Не мигрировать произвольные пользовательские исходники автоматически.  
    **Приёмка:** миграции тестируются на старых fixtures; повторное применение безопасно; отказ оставляет исходные данные целыми.

17. **Конкурентный доступ.** Использовать document version, generation counter, file lock или optimistic conflict check для параллельных изменений из Studio, LSP и фоновых задач.  
    **Приёмка:** устаревшая запись не перезаписывает новую; конфликт возвращает ожидаемую и фактическую версии.

18. **Ограниченные списки и выборки.** Каталоги символов, diagnostics, CODEX-66 и toolchain inventory должны поддерживать лимиты, фильтрацию и постраничную/ленивую выдачу там, где коллекции могут расти. SQL-пагинация не нужна без SQL-хранилища.  
    **Приёмка:** большие workspace/catalogue не приводят к неограниченному потреблению памяти; лимиты отражаются в ответе.

19. **Индексы под реальную нагрузку.** Строить индексы символов, references, source maps и файлов только для наблюдаемых запросов; явно инвалидировать их по версии документа/проекта. Не вводить database indexes без БД.  
    **Приёмка:** benchmark фиксирует ускорение целевого сценария; устаревший индекс не возвращает ложные позиции.

20. **Разделение интерактивной и тяжёлой работы.** Диагностика открытого файла не должна ждать полного workspace audit, массового экспорта, долгой линковки или анализа сторонних toolchain.  
    **Приёмка:** интерактивные операции имеют отдельный бюджет задержки; тяжёлые задачи выполняются отдельно и сообщают прогресс/отмену.

21. **Время и часы.** В audit и persisted metadata использовать UTC; для измерения длительности — монотонные часы. Локальную временную зону применять только при отображении.  
    **Приёмка:** тесты перехода даты/часового пояса не меняют порядок событий и длительности.

22. **Безопасное удаление и архив.** Удаление project profile, generated output или audit artifacts должно быть явным, ограниченным разрешённым корнем и по возможности восстанавливаемым. Исходники и пользовательские файлы не удаляются как побочный эффект проверки/сборки.  
    **Приёмка:** path traversal и symlink escape тесты блокируются; удаление требует конкретной цели.

23. **Резервирование и восстановление.** Защищать пользовательские конфигурации, профили и важные локальные журналы; проверять процедуру восстановления, а не только создание копии. Сгенерированные кэши могут пересоздаваться и не должны считаться единственным источником правды.  
    **Приёмка:** restore test поднимает валидное состояние из копии; повреждённый backup не перезаписывает оригинал.

24. **Контроль пустых и повреждённых значений.** Не подменять повреждённый профиль молча пустым объектом или опасными defaults. Применять миграцию/repair только с диагностикой и сохранением исходника.  
    **Приёмка:** malformed state даёт понятный статус; восстановление не скрывает факт повреждения.

### III. Производительность, ресурсы и масштабирование (25–36)

25. **Измерять до оптимизации.** Ввести reproducible benchmarks для lexer/parser, semantic analysis, runtime, LSP completion, indexing, native lowering и build pipeline. Измерять CPU, wall time, peak memory и размер outputs.  
    **Приёмка:** оптимизация сопровождается baseline, повторным измерением и отсутствием семантических регрессий.

26. **Ограничивать входные объёмы.** Сохранять и централизовать лимиты размера source/module, глубины AST/JSON, количества diagnostics, элементов коллекций, размера текста, heap estimate, call depth, steps и открытых ресурсов.  
    **Приёмка:** каждый лимит имеет тест на значение ниже, на границе и выше лимита.

27. **Таймауты внешних операций.** Compiler/linker/debugger/Node/npm и другие внешние процессы должны иметь timeout, cancellation и ограниченное ожидание завершения. Чистые локальные вычисления ограничиваются budget/step counters, где wall-clock timeout неуместен.  
    **Приёмка:** зависший subprocess завершается по timeout; пользователь получает код ошибки и сведения об операции.

28. **Переиспользование ресурсов.** Переиспользовать безопасные immutable toolchain descriptors, parsed configuration и долгоживущие worker-процессы, если это подтверждено профилированием. Не держать открытые файлы/процессы без владельца.  
    **Приёмка:** ресурс имеет явный owner/lifecycle; повторная команда не создаёт утечку процессов/дескрипторов.

29. **Устранение N+1 в локальных сервисах.** Пакетно собирать symbol/reference data, читать модули и вычислять diagnostics вместо повторного обхода одного документа для каждого элемента интерфейса.  
    **Приёмка:** тест/benchmark на большом workspace подтверждает ограниченное число проходов и не ухудшает актуальность данных.

30. **Осмысленное кэширование.** Ключ кэша включает хэш source, compiler/runtime version и target/config fingerprint. TTL/инвалидация — только для данных, зависящих от времени; immutable результатов предпочтителен content-addressed cache.  
    **Приёмка:** изменение исходника, версии или target profile не возвращает старый результат; повреждённый cache безопасно пересоздаётся.

31. **Потоковая обработка крупных данных.** Большие logs, binary artifacts, source bundles и JSONL audit читать/писать потоково; не загружать неограниченный файл целиком.  
    **Приёмка:** memory test показывает ограниченное потребление при увеличении входного файла.

32. **Контроль фоновых задач.** Очереди сборки/indexing ограничены; задачи имеют cancellation token, deadline, lifecycle и ясный результат. Ошибочные задачи не запускаются бесконечно и не создают бесконтрольные повторные попытки.  
    **Приёмка:** при перегрузке очередь отклоняет/объединяет дублирующую работу с понятным статусом.

33. **Не блокировать UI и protocol loop.** Длительный compiler/linker subprocess и тяжёлые вычисления выносить из UI thread; stdio protocol loop должен своевременно принимать shutdown/cancel и не смешивать protocol output с логами.  
    **Приёмка:** UI остаётся отзывчивым; stdout содержит только protocol frames; stderr предназначен для диагностических сообщений.

34. **Жизненный цикл ресурсов.** Файлы, subprocess, pipes, sockets (если явно используются), locks, worker threads и temporary directories закрываются в finally/context manager/shutdown path.  
    **Приёмка:** повторные циклы запуска/остановки не увеличивают число открытых handles/processes.

35. **Масштабирование в пределах продукта.** Не привязывать общие project settings и контракты к одной UI-сессии; поддерживать корректные конфликты между несколькими окнами/процессами. Горизонтальный кластер и sticky sessions не внедрять, пока Reaper остаётся локальным single-machine инструментом.  
    **Приёмка:** параллельные локальные процессы обнаруживают конфликт записи; кластерные гарантии не заявляются.

36. **Безопасная деградация.** При исчерпании квот, недоступности optional toolchain, повреждении кэша или отказе второстепенного сервиса сохранить возможность безопасного просмотра/проверки доступных данных. Не продолжать опасную операцию на неполных данных.  
    **Приёмка:** fault-injection tests подтверждают read-only/fail-closed поведение и ясное сообщение.

### IV. Отказоустойчивость, процессы и протоколы (37–46)

37. **Считать внешние инструменты ненадёжными.** Проверять exit code, stdout/stderr, timeout, путь исполняемого файла, версию и ожидаемый формат результата. Данные subprocess не считать доверенными.  
    **Приёмка:** fake compiler/process tests покрывают зависание, неверный вывод, преждевременное завершение и отсутствующий executable.

38. **Ограниченные retry.** По умолчанию не повторять неидемпотентные команды и не повторять ошибки валидации. Для безопасных повторяемых запросов к внешнему инструменту задавать максимальное число попыток, exponential backoff и jitter.  
    **Приёмка:** retry policy тестируется детерминированным random/clock source; retry storm невозможен.

39. **Circuit breaker только для реальных зависимостей.** Применять breaker к повторяющимся сбоям удалённого или долгоживущего адаптера, если такой адаптер реально поддерживается. Не добавлять декоративный breaker к чистым локальным функциям или несуществующему backend endpoint.  
    **Приёмка:** open/half-open/closed состояния тестируются на adapter boundary; recovery не блокирует обычный локальный runtime.

40. **Graceful shutdown.** При завершении Studio worker, LSP/DAP или build job перестать принимать новую работу, отправить корректный protocol response, отменить/дождаться активные задачи в пределах deadline и закрыть ресурсы.  
    **Приёмка:** shutdown tests покрывают idle, active и failed task; процесс не зависает бесконечно.

41. **Разделять alive и ready.** Для локальных сервисов readiness означает, что протокол и зависимости инициализированы и запросы безопасно принимаются; liveness — что процесс не завис и может реагировать. HTTP health endpoints не добавлять без HTTP-сервиса.  
    **Приёмка:** lifecycle state проверяется unit/integration tests и корректно отражается в Studio/CLI.

42. **Защита от повторных и устаревших сообщений.** LSP document version, DAP sequence, task generation и transaction generation сверяются прежде чем применить ответ/изменение.  
    **Приёмка:** старое событие и дубликат не перезаписывают новое состояние; нарушение sequence диагностируется.

43. **Единые кодировки и framing.** Внешние текстовые контракты используют UTF-8; LSP/DAP Content-Length framing проверяется по байтам; JSON разбирается строго, без неоднозначных дублирующихся ключей там, где контракт этого требует.  
    **Приёмка:** тесты с кириллицей, emoji, некорректным UTF-8, усечёнными frame и неверным length.

44. **Изоляция второстепенных контуров.** Toolchain inventory, telemetry, отчётная упаковка и optional integration не должны ломать syntax checking или запуск базовой программы, если они не являются обязательной зависимостью операции.  
    **Приёмка:** отказ optional adapter не нарушает базовый сценарий; required adapter завершает операцию явно.

45. **Повторы неидемпотентных действий — только с защитой.** Не повторять установку пакета, запись/удаление, прошивку устройства или запуск пользовательской команды вслепую. Для каждого будущего destructive action нужны явное согласие, capability, audit и recovery plan.  
    **Приёмка:** по умолчанию такие действия не повторяются автоматически; отсутствие согласия блокирует действие.

46. **Частичный успех описывать явно.** Batch toolchain discovery, multi-file diagnostics, project migration и массовые проверки возвращают per-item success/failure/skip, не превращая частичный результат в общий success.  
    **Приёмка:** contract tests проверяют смешанный результат; summary соответствует фактическим элементам.

### V. Безопасность, права и защита данных (47–56)

47. **Наименьшие привилегии.** Interpreter, plugin, subprocess и native adapter получают только необходимый доступ. Native FFI, MMIO, process launch, filesystem mutation и hardware actions — отдельные явные capabilities.  
    **Приёмка:** отсутствие capability блокирует операцию; grant ограничен scope и сроком, если применимо.

48. **Проверка прав на каждой защищённой операции.** Проверять capability непосредственно перед действием, а не только при открытии проекта или запуска Studio. Отделять идентификацию вызывающего субъекта от разрешения конкретной операции.  
    **Приёмка:** негативные тесты обхода через альтернативный entry point не проходят.

49. **Защита объектов и путей.** Локальные ID/URI/пути не дают автоматического права читать или изменять файл. Канонизировать путь, проверять разрешённый workspace root и symlink escape.  
    **Приёмка:** ID/path traversal, symlink и подмена URI проверяются; доступ за границу workspace отклоняется.

50. **Секреты не входят в репозиторий и результаты.** Не сохранять credentials, tokens, private keys и secrets в коде, примерах, audit и error payload. Использовать OS secret storage только для функций, которым реально нужны credentials.  
    **Приёмка:** secret scanning и redaction tests; отчёт не содержит совпавшего секрета.

51. **Криптография — по назначению.** Для подписи артефактов использовать проверяемую подпись и доверенную цепочку; для паролей — только если появится локальная account/authentication feature, использовать Argon2id/bcrypt с управляемой солью. Hash chain аудита не называть цифровой подписью или доказательством внешней подлинности.  
    **Приёмка:** проверяется origin/signature артефактов; документация точно описывает пределы SHA-256/HMAC.

52. **Защита от injection и unsafe deserialization.** В subprocess вызывать executable и аргументы отдельными элементами списка, не через shell string; ограничить динамическую загрузку, JSON/YAML parsing и plugin entry points явными схемами.  
    **Приёмка:** payload/path с shell metacharacters не меняет команду; неизвестные типы/поля отклоняются.

53. **Контроль злоупотребления ресурсами.** Защищать parser, LSP, DAP evaluate, plugin API и project scanning лимитами размера, глубины, частоты дорогих операций и времени. Для локального инструмента предпочитать bounded work/cancellation вместо сетевого rate limiter.  
    **Приёмка:** stress tests подтверждают ограниченную стоимость невалидного запроса.

54. **Безопасность транспорта.** Основные LSP/DAP каналы остаются stdio. Для явно поддержанного сетевого адаптера потребуются TLS, authentication, origin policy и отдельный security review; CORS не относится к stdio и не должен имитироваться.  
    **Приёмка:** сетевые listener не открываются неожиданно; protocol transport указан явно в документации.

55. **Маскирование чувствительных сведений.** Перед логированием нормализовать поля с credentials, private paths, environment values и пользовательским содержимым; не записывать полный source code без отдельного явного режима.  
    **Приёмка:** тесты проверяют, что redacted fields не восстанавливаются из логов и отчётов.

56. **Минимальная поверхность атаки.** По умолчанию не запускать Node Inspector, remote debug, native FFI, flashing, network listener и privileged device operations. Включать только по явному запросу и проверенному профилю.  
    **Приёмка:** secure defaults tests проверяют отсутствие незапрошенных listener/process/effects.

### VI. Наблюдаемость, тестирование, выпуск и эволюция (57–66)

57. **Структурированные события и correlation ID.** Каждая команда/build/debug session получает operation_id; для цепочки компонентов передаётся trace/correlation ID. Логи — локальные и с redaction.  
    **Приёмка:** один ID связывает CLI/Studio operation, adapter call и audit record без записи секретов.

58. **Измеримые метрики.** Фиксировать duration, throughput, cache hit/miss, queue depth, cancellation, resource-limit hits и errors для ключевых операций. Percentiles p50/p95/p99 использовать в benchmark/CI, а не объявлять без измерений.  
    **Приёмка:** benchmark artifacts воспроизводимы и сравнимы между commit/target; метрики не подменяют correctness tests.

59. **Трассировка этапов.** Компиляция должна позволять определить время lexer, parser, semantic analysis, IR verification, lowering, external compiler и linker. Для локальной цепочки достаточно span/event trace; распределённую tracing-инфраструктуру не вводить без распределённых сервисов.  
    **Приёмка:** медленный этап локализуется по operation_id; trace не меняет семантику программы.

60. **Оповещения по реальному влиянию.** CI должен блокировать воспроизводимые регрессии, нарушение security policy, ошибку schema и отказ обязательного теста. Не создавать шумные алерты на незначительные локальные колебания.  
    **Приёмка:** каждый blocking check имеет владельца, понятный текст ошибки и remediation.

61. **Многоуровневые тесты.** Unit — чистая логика; integration — runtime/FS/protocol/toolchain adapters; differential — Python vs native для общего подмножества; fuzz/property — lexer/parser/JSON/IR; smoke — CLI/Studio packaging; load/stress — resource bounds.  
    **Приёмка:** изменение не проходит merge без релевантных тестов; native parity ограничена реально покрытыми конструкциями.

62. **Воспроизводимая сборка.** Зафиксировать версии build tools, Python, C compiler и optional Node compatibility matrix; CI должен одинаково проверять lint/format, tests, schemas, docs links и packaging.  
    **Приёмка:** чистый checkout собирается по опубликованным командам; версия и источник toolchain отражены в build evidence.

63. **Безопасный выпуск и откат.** Release artifacts привязываются к commit, имеют checksum/provenance и, где настроено, подпись. Предыдущая версия должна оставаться доступной; миграции persisted state должны иметь rollback или безопасный forward-recovery.  
    **Приёмка:** release verification и restore/rollback procedure проходят на тестовом артефакте.

64. **Документация соответствует коду.** Для каждого публичного API/protocol/schema описывать версии, входы, выходы, ошибки, effects, limits, supported targets и maturity. Обновлять feature matrix только после тестового подтверждения.  
    **Приёмка:** ссылки/примеры проверяются CI; статусы Available/Experimental/Planned сверяются с кодом и тестами.

65. **Удалять мёртвый код и устаревшие контракты.** Удаление проводится после поиска всех call sites, migration/compatibility review и тестов. Не удалять reserved syntax/API молча, если это меняет совместимость.  
    **Приёмка:** dead code не остаётся активным entry point; удалённый контракт имеет release note/deprecation path при необходимости.

66. **Backend незаметен, но проверяем.** Runtime должен быть предсказуемым, ограниченным, безопасным и понятным при отказе. Любая заявленная возможность подтверждается исходником, тестом, схемой и evidence; планы и registry entries не выдаются за работающую функцию.  
    **Приёмка:** release gate не допускает статус «implemented» без исполняемого end-to-end сценария и соответствующих тестов.

## 3. Сопоставление с существующим фундаментом

Следующие элементы уже обнаружены в репозитории как код или документированные контракты; перед продвижением статуса требуется повторная проверка кода и тестов:

- \`reaper/transactions.py\` и \`tests/test_transactions.py\`: optimistic generation, snapshots, conflicts, rollback и миграционная модель состояния.
- \`reaper/audit.py\`: локальный JSONL hash chain, проверка последовательности и digest; это tamper-evidence, не подпись.
- \`reaper/lsp.py\`, \`reaper/dap.py\`: stdio protocol adapters; DAP read-only evaluate ограничивает выражения и глубину.
- Runtime quotas: steps, call depth, collections, text, heap estimate и open resources; heap estimate не является OS memory sandbox.
- \`tools/report_envelope.py\` и \`schemas/ivan-vhs.report.v1.schema.json\`: versioned JSON report envelope.
- \`include/reaper/hardware.h\`: проверяемый MMIO descriptor/adapter contract; не выполняет физическое отображение памяти.
- \`.architecture/resilience-policy.json\`: политика описана как \`contract_only\`; её поля не считаются доказательством runtime enforcement.
- \`SECURITY.md\` и \`security/beelzebul.v1.json\`: security scanning и governance catalog; автоматический скан не доказывает отсутствие уязвимостей.

## 4. Что не следует добавлять ради формального соответствия

Пока Reaper остаётся локальным инструментом, не внедрять без отдельного продуктового требования: публичный HTTP backend, SQL/NoSQL database, CORS, web sessions, JWT accounts, distributed queue/broker, cluster orchestration, sticky sessions, distributed tracing platform или горизонтальные health endpoints. Не добавлять парольное хранилище, если в продукте нет собственной account-системы. Не реализовывать реальный MMIO/IRQ/DMA без доверенного OS/HAL adapter, платформенного контракта и hardware qualification.

Применимость правила не отменяется: его локальный эквивалент должен быть закрыт в правильном контуре — например, bounded worker queue вместо distributed broker, operation_id вместо HTTP request_id, schema validation вместо database constraints, atomic file replacement вместо SQL transaction.

## 5. Очерёдность внедрения

**Этап A — контрактная основа:** единая error model; общие validators; versions для JSON/ABI/protocols; dependency boundaries; resource limits; source-aware diagnostics.

**Этап B — надёжные данные и операции:** atomic file writes; migrations/backups для persisted profiles; generation/version conflicts; path confinement; idempotent commands; audit redaction.

**Этап C — внешние процессы и отзывчивость:** timeout/cancellation/shutdown для subprocess и workers; bounded queues; strict framing; toolchain validation; cache invalidation; UI responsiveness.

**Этап D — безопасность:** capability checks на всех entry points; safe subprocess invocation; plugin isolation policy; secure defaults; secret scanning/redaction; native adapter boundary tests.

**Этап E — измеримость и выпуск:** benchmarks, operation IDs, phase timing, fuzz/differential tests, reproducible builds, release provenance, rollback drills и синхронизация документации.

Порядок внутри этапа можно менять только с указанием зависимости и риска. Не делать массовый rewrite до фиксации baseline и тестов.

## 6. Общие условия приёмки

- Все 66 пунктов получают статус \`implemented\`, \`partial\`, \`planned\` или \`not_applicable\` с кратким обоснованием и ссылкой на код/тест/схему.
- \`not_applicable\` допустим только для отсутствующей продуктовой поверхности и должен быть заменён корректным локальным эквивалентом там, где это нужно.
- Для каждого изменённого контракта добавляются позитивные, негативные и граничные тесты.
- Python reference semantics не меняются случайно; native C17 parity заявляется только для покрытого подмножества.
- Никакие новые capabilities не получают привилегии по умолчанию.
- Все долговременные операции ограничены ресурсами, отменяемы там, где это возможно, и не оставляют частичного corrupt state.
- Документация, feature registry и release notes не опережают реальное состояние кода.
- Финальный отчёт содержит список изменённых файлов, команды тестов, результаты, оставшиеся ограничения и точные commit/PR ссылки.

**Принцип:** внедрять не абстрактный веб-бэкенд, а надёжный backend Reaper — ядро компиляции и исполнения, локальные протоколы, адаптеры, состояние проекта и проверяемый жизненный цикл ресурсов.
