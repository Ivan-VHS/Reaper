# Reaper — инженерный профиль языка и компилятора

**Проект:** Ivan-VHS/Reaper  
**Автор инженерного направления:** Ivan-VHS  
**Статус документа:** целевая архитектура и критерии развития; описанные этапы не считаются реализованными до прохождения тестов.

## Назначение

Reaper развивается как самостоятельный язык программирования, компиляторная система и набор инструментов разработчика. Его отличительные черты — потоковая композиция через оператор `::`, читаемый синтаксис, предсказуемая семантика и возможность постепенно перейти от reference runtime к нативному исполнению.

## Основной стиль кода

Практические правила читаемости, границ, безопасности и проверки вынесены в единый стандарт [Ivan-VHS Code Style](IVAN_VHS_CODE_STYLE.md). Он задаёт общий характер инженерной работы, не подменяя язык, formatter или архитектурные контракты конкретного проекта.

## Инженерные принципы

1. **Семантика прежде синтаксического изобилия.** Каждое ключевое слово, оператор и alias имеют одно документированное значение, примеры и негативные тесты.
2. **Один смысл — несколько backend.** Reference runtime, native compiler и DAK target должны проходить общий набор семантических тестов.
3. **Промежуточные представления — проверяемые границы.** HIR, MIR и LIR имеют валидаторы инвариантов и диагностические дампы.
4. **Читаемый код языка важнее декоративной сложности.** Встроенные функции короткие и композиционные; ошибка объясняет строку, колонку, контекст и способ исправления.
5. **Никаких фиктивных статусов.** Реализованное, частично реализованное, reference-only и запланированное различаются в документации, CLI и CI.

## Целевой конвейер

`source → lexer → parser → AST → semantic analysis → HIR → MIR → LIR → object → linker/loader → runtime`

### Контракты этапов

| Этап | Выход и инвариант |
|---|---|
| Lexer | токены с исходными диапазонами; некорректная последовательность не теряется молча |
| Parser | AST с детерминированными правилами приоритета и восстановления после ошибки |
| Semantic analysis | разрешённые имена, типы, области видимости и проверенные вызовы |
| HIR | конструкции языка представлены независимо от деталей backend |
| MIR | явные базовые блоки, переходы, локальные значения и точки возврата |
| LIR | операции приведены к контракту конкретной целевой архитектуры |
| Object generation | секции, символы, relocations и формат объекта проверяются до записи |
| ABI | calling convention, типы, владение, ошибки и версия интерфейса задокументированы |
| Runtime | выделение ресурсов, исключения/ошибки и системные вызовы имеют явные границы |

## Семантика оператора `::`

Оператор должен иметь одну основную модель композиции: значение слева передаётся в следующий этап справа. Спецификация обязана определить приоритет, ассоциативность, поведение с несколькими аргументами, передачу владения и обработку ошибок. Выражение вычисляется один раз, если спецификация явно не говорит обратного. Алиасы не должны создавать альтернативную семантику.

## Минимальные вертикальные срезы

1. **Срез выражений:** литерал → AST → вычисление → диагностический результат.
2. **Срез функций:** объявление → параметры → локальные переменные → вызов → возврат.
3. **Срез управления:** блоки → условие → цикл → корректные переходы и точки выхода.
4. **Срез компилятора:** один модуль → HIR/MIR/LIR → объектный файл → запуск.
5. **Срез DAK ABI:** вызов маленькой системной функции из Reaper-программы через версионированный ABI; ошибка ABI должна обнаруживаться до исполнения.

## DAK ABI: обязательные вопросы до реализации

- целевая архитектура и размер слова;
- calling convention и выравнивание;
- представление строк, массивов и структур;
- правила владения памятью и время жизни;
- передача ошибок и unwind policy;
- таблица системных вызовов и capability checks;
- версия ABI, совместимость и поведение при неизвестной версии.

ABI не должен быть прямым отображением внутренних Python-объектов или структур компилятора. Это самостоятельный, стабильный контракт между программой и системой.

## Проверки компилятора

- golden-тесты токенов, AST и диагностик;
- одинаковые семантические тесты для reference runtime и native backend;
- property/fuzz-тесты lexer/parser с лимитом времени и памяти;
- отрицательные тесты областей видимости, типов, арности и невалидных переходов;
- проверка HIR/MIR/LIR после каждого lowering;
- тест round-trip символов и relocations для объектной генерации;
- ABI conformance tests с версионированием.

## Принцип реализации

Новые функции сначала проходят путь «спецификация → небольшой исполняемый пример → тест → документация → интеграция в Studio/LSP». Не создавать одновременно десятки синтаксических конструкций, если один сквозной сценарий ещё не компилируется и не запускается. Каждый модуль должен иметь ясное назначение и минимальное количество скрытых глобальных состояний.

## Граница обещаний

Наличие AST, каталога функций, Python-интерпретатора или экспериментального C-кода само по себе не доказывает наличие законченного нативного компилятора. Пока объектная генерация и запуск не проходят conformance suite, native track обозначается как частичный.

**Итоговая формула Reaper:** точная грамматика → явная семантика → валидируемые IR → стабильный ABI → работающая программа.
