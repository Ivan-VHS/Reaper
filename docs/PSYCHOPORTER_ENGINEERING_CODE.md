# Psychoporter Engineering Code — Ivan-VHS System Architecture

**Статус:** нормативный стиль и инженерная доктрина для Reaper; синтаксические правила привязаны к подтверждённому состоянию языка и помечают будущие возможности отдельно.
**Область:** исходники `.rpr`, язык и компилятор Reaper, reference runtime, native C17 track, Reaper Studio, LSP/DAP, тесты, документация и интеграции.
**Назначение:** сделать код когнитивно ясным, технически честным, безопасным, сопровождаемым и человечным — без псевдонаучных обещаний и архитектуры ради украшения.

## Как читать и применять Кодекс

The XI domain contains 60 practical principles (601–660) and six closing principles (661–666). Together, the domains form the complete engineering code and its final principles.

Кодекс не является психологическим тестом, диагнозом или научно доказанной нейробиологической моделью. Психологический портрет и взгляд близкого человека используются только как добровольный контекст проектирования эргономики: концентрация, авторская автономия, чувствительность к качеству, склонность к широким замыслам, необходимость завершать работу и сохранять баланс. Фотография не используется для вывода о характере.

### Уровни нормативности
- **CURRENT** — подтверждённая текущая поверхность Reaper: `craft`, `make`, `vary`, `change`, `yield`, `emit`, `when`, `otherwise`, `each`, `loop while`, оператор потока `::` и существующие runtime/tooling contracts.
- **TARGET** — желаемые расширения: полноценные типы `Result`, ownership/borrowing, effects, HIR/MIR/LIR parity, native backend и системные контракты. Их нельзя представлять как реализованные до прохождения acceptance gates.
- **HOST** — обязанности reference host, native C17 substrate, Studio, ОС или платформенного адаптера. Host-код не является синтаксисом Reaper.

Текущий репозиторий использует Python reference runtime и частичный native C17 track; документация и feature matrix определяют фактическую зрелость. Reaper-код не должен получать скрытые filesystem, network, shell, FFI или hardware полномочия. Оператор `::` является текущим flow operator; `|>` не приводится как действующий синтаксис текущей версии.

### Главные инженерные законы
- **Intent clarity:** намерение видно из имён, границ и последовательности.
- **Explicit contracts:** типы, ограничения, эффекты, владение и ошибки обозначены явно.
- **Bounded behavior:** циклы, память, входные данные, повторные попытки и время имеют пределы.
- **Evidence-based maturity:** статус функции определяется исходниками, тестами и интеграцией.
- **Human layer:** качество системы не оправдывает унижение, истощение или потерю автономии людей.

## I. Имя и сущность — семантика Reaper

*Идентификаторы должны сокращать путь от намерения к пониманию.*

1. Имя связывает идентификатор с одним устойчивым смыслом и контрактом.
2. Выбирай имя по предметной области, а не по типу контейнера.
3. Не называй значимые значения data, temp, object или value без контекста.
4. Короткое имя допустимо, когда его смысл очевиден внутри локальной функции.
5. Длинное имя оправдано, если оно устраняет реальную неоднозначность.
6. Не измеряй качество имени количеством слогов или символов.
7. Используй единый стиль lower_snake_case для обычных имён Reaper-кода.
8. Сохраняй текущую грамматику Reaper; не выдумывай синтаксис ради именования.
9. Имена craft-функций начинай с точного глагола действия.
10. Имя функции должно раскрывать действие и объект воздействия.
11. Не добавляй get или set, если они не уточняют семантику.
12. Булевы значения называй как проверяемые свойства: is_ready, has_access, can_retry.
13. Избегай двойных отрицаний в именах логических значений.
14. Отличай inactive от not_active только при реальном различии модели.
15. Имена неизменяемых make-связей должны передавать смысл, а не изменяемость.
16. Имена vary-связей должны показывать роль изменяемого состояния.
17. Не используй суффиксы вроде final, new или latest без временного контракта.
18. Не кодируй в имени сведения, которые гарантированно выводятся из типа.
19. Не используй номер задачи вместо предметного имени.
20. Не называй функцию handle_event, если известен конкретный тип события.
21. Не называй компонент manager, если его ответственность можно назвать точнее.
22. Слова util, common и helper допустимы только для действительно общих контрактов.
23. Не создавай универсальный модуль, который собирает несвязанные операции.
24. Типовые имена должны отличать доменную сущность от технического представления.
25. Для публичных терминов веди единый словарь Reaper.
26. Один термин должен обозначать одно понятие во всех модулях.
27. Не вводи синонимы только ради стилистического разнообразия.
28. Сокращай только общеизвестные или локально расшифрованные термины.
29. Не используй сокращение, смысл которого известен лишь автору сегодня.
30. Единицы измерения указывай в имени, когда тип их не фиксирует.
31. Различай bytes, items, ticks, milliseconds и pages в названиях.
32. Для размеров и смещений указывай единицы либо специализированный тип.
33. Имена адресов должны различать physical, virtual и bus address.
34. Имена буферов должны указывать содержимое и стадию обработки.
35. Имена идентификаторов должны указывать пространство имён и область уникальности.
36. Отличай source_span от byte_offset и line_column.
37. Не называй Span переменной position, если это диапазон исходника.
38. Имена ошибок должны раскрывать причину или нарушенный контракт.
39. Используй стабильные диагностические коды RPR-E, RPR-T и согласованные семейства.
40. Не меняй смысл существующего кода диагностики между версиями.
41. Имена тестов должны описывать сценарий и ожидаемый результат.
42. Имена фикстур должны называть исходное состояние, а не номер набора.
43. Имена mock-объектов должны раскрывать заменяемую границу.
44. Имена модулей должны совпадать с их ответственностью и каталогом.
45. Имена публичных API должны быть стабильными и предметными.
46. Имена внутренних функций могут быть короче при локальной ясности.
47. Не используй эмоциональную окраску вместо технической точности.
48. Слова terminate, destroy и revoke допустимы, когда точно описывают действие.
49. Не смягчай опасную операцию названием, которое скрывает её последствия.
50. Имена capability должны выражать конкретное право и ограниченный ресурс.
51. Имена эффектов должны обозначать наблюдаемое внешнее воздействие.
52. Имена целевых профилей должны включать архитектуру, ABI и среду исполнения.
53. Имена артефактов должны содержать версию, target и воспроизводимый fingerprint.
54. Имена конфигураций должны явно различать debug, release и qualification.
55. Имена веток отражают область и намерение изменения.
56. Сообщение коммита начинается с действия и называет изменённый контракт.
57. Имена переменных окружения должны иметь уникальный префикс продукта.
58. Публичные имена не должны зависеть от названия текущего файла.
59. Не переименовывай внешний контракт без миграции и заметки о совместимости.
60. При рефакторинге обновляй имена, комментарии, документацию и тесты вместе.

## II. Синтаксис и поток мысли Reaper

*Синтаксис должен показывать последовательность вычисления без маскировки сложности.*

61. Читай Reaper-код сверху вниз как последовательность намерений.
62. Показывай основной сценарий до редких ветвей, если это не скрывает безопасность.
63. Используй раннюю проверку некорректного состояния, когда грамматика и поток это поддерживают.
64. Не помещай важную работу в глубоко вложенные ветви.
65. Старайся удерживать вложенность в пределах двух-трёх смысловых уровней.
66. Если вложенность растёт, выдели отдельную craft-функцию с точным именем.
67. Один блок должен представлять одну законченную операцию или фазу.
68. Разделяй блоки пустой строкой, когда меняется смысловой шаг.
69. Не выравнивай пробелами несвязанные строки ради декоративной геометрии.
70. Соблюдай единые отступы во всех .rpr-файлах.
71. Оставляй пробелы вокруг бинарных операторов.
72. Сохраняй единое форматирование аргументов вызовов.
73. Переноси длинные аргументы так, чтобы каждый оставался различимым.
74. Не объединяй несколько независимых изменений в одну строку.
75. Используй make для неизменяемого связывания значения.
76. Используй vary только для состояния, которое действительно меняется.
77. Используй change явно для изменения существующей vary-связи.
78. Не маскируй мутацию под вычисление нового значения.
79. Применяй craft для именованного поведения, а не ради каждой строки.
80. Используй yield как явный результат функции в текущей модели языка.
81. Используй emit для явно наблюдаемого вывода, а не скрытой диагностики.
82. Используй when и otherwise в соответствии с действующей грамматикой.
83. Не переносите в Reaper if/else-синтаксис из других языков без поддержки грамматики.
84. Применяй each для обхода коллекции, когда это выражает намерение.
85. Применяй loop while только при состоянии, меняющемся в теле цикла.
86. Для каждого цикла документируй или доказывай условие завершения.
87. Бесконечный цикл допустим только в явно обозначенной системной петле с остановкой.
88. Не используй рекурсию без базового случая и ограничений глубины.
89. Для рекурсивных обходов учитывай размер входа и лимит стека.
90. Оператор :: является текущим оператором потока Reaper.
91. Не заменяй :: на |> в примерах, тестах или документации текущей версии.
92. Располагая шаги через ::, сохраняй слева направо понятный поток данных.
93. Передавай в :: преобразования с ясным входом и выходом.
94. Не создавай длинную цепочку ::, если промежуточные состояния теряют смысл.
95. Выноси именованные преобразования в craft-функции.
96. Используй map для преобразования, keep для отбора и fold для свёртки.
97. Не используй map там, где требуется побочный эффект или управление ресурсом.
98. Не смешивай очистку, фильтрацию и агрегацию в одной безымянной операции.
99. Сохраняй порядок вычисления, если от него зависит результат.
100. Не полагайся на неоговорённый порядок обхода коллекции.
101. Не используй условный оператор или сокращённую форму, если она ухудшает обзор.
102. Сложное условие сначала разложи на именованные предикаты.
103. Проверяй граничные случаи до чтения индекса или элемента.
104. Проверяй размер коллекции до дорогого преобразования.
105. Явно обозначай ограничения размера текста и коллекций.
106. Не скрывай преобразование типов в неочевидном выражении.
107. Не допускай неявного сужения чисел на границах системного ABI.
108. Разделяй синтаксический разбор и вычисление.
109. Не смешивай построение AST с выполнением программы.
110. Сохраняй source location при каждом преобразовании AST.
111. Не удаляй Span при lowering без сохранения SourceMap.
112. Различай синтаксическую ошибку, семантическую ошибку и ошибку исполнения.
113. Сохраняй точную область действия переменной.
114. Не используй переменную после завершения области её смысловой ответственности.
115. Сгруппируй связанные make/vary-связи перед первым использованием, если так яснее.
116. Не объявляй значения заранее только ради большой шапки функции.
117. Возвращай результат в одном очевидном месте, когда это упрощает понимание.
118. Несколько выходов допустимы, если каждый соответствует явному раннему отказу.
119. Не создавай чрезмерно длинные функции ради линейного чтения.
120. Разделяй большие функции по этапам предметного процесса.

## III. Архитектура и карта системы

*Модули образуют направленный граф контрактов, а не коллекцию файлов.*

121. Группируй исходники по возможностям и предметным границам.
122. Держи связанные .rpr-файлы рядом с тестами и документацией модуля.
123. Не дроби проект на папки по расширениям без практической причины.
124. Файл должен иметь одну ведущую ответственность.
125. Разделяй публичный контракт и внутреннюю реализацию.
126. Публичный интерфейс объясняет назначение, входы, выходы и ограничения.
127. Скрывай детали, которые не нужны вызывающему модулю.
128. Не скрывай важные эффекты за декларативным именем.
129. Зависимости должны иметь явное направление.
130. Нижний слой не должен импортировать верхний слой приложения.
131. Ядро языка не должно зависеть от Studio.
132. Studio использует языковое ядро через стабильные сервисы.
133. CLI, LSP и DAP не должны создавать параллельную грамматику.
134. MOST нормализует поддерживаемые алиасы до общей семантики.
135. QCS остаётся отдельным инструментом проверки аппаратного домена.
136. Native C17 track не объявляется эквивалентным reference runtime без parity evidence.
137. Python reference implementation остаётся совместимостным эталоном до закрытия parity gates.
138. Реализационная миграция не должна менять семантику незаметно.
139. Разделяй frontend, semantic analysis, IR, optimization и backend.
140. Каждый этап компилятора имеет проверяемый входной и выходной контракт.
141. Канонический IR должен быть версионированным и документированным.
142. HIR хранит типизированное намерение высокого уровня.
143. MIR отражает поток управления, владение, эффекты и освобождение ресурсов.
144. LIR отражает операции, близкие к целевому ABI.
145. Не смешивай AST и IR в одну неразличимую структуру.
146. Каждый IR verifier проверяет форму, типы, ссылки и control-flow edges.
147. Не принимай непроверенный IR в backend.
148. SourceMap сохраняет происхождение узлов до итогового артефакта.
149. Span имеет определённую систему координат и единицы смещения.
150. Стабильные контракты сериализации должны иметь версию.
151. Ломающие изменения требуют миграции и compatibility note.
152. Внешние зависимости фиксируются в lock-файле или manifest.
153. Зависимость добавляется только при явной ценности и оценённой цене сопровождения.
154. Не дублируй функциональность стандартной библиотеки без причины.
155. Не связывай продукт с сетью по умолчанию.
156. Hosted и freestanding профили должны быть разными контрактами.
157. Boot, kernel, driver, MCU и hosted targets имеют явные профили.
158. Целевой triple, ABI и CPU features входят в build profile.
159. Memory map и linker layout не должны выводиться из догадок.
160. Адресные пространства физической, виртуальной и DMA-памяти разделены.
161. MMIO доступен только через проверенный platform adapter.
162. Ни один обычный пользовательский модуль не получает произвольное право MMIO.
163. DMA-буфер имеет владельца, срок жизни и согласованный cache protocol.
164. IRQ-контекст имеет ограничения на блокировки и выделение памяти.
165. Не выполняй потенциально блокирующую операцию в interrupt context.
166. Системные вызовы являются границей привилегий, а не внутренним API каждого модуля.
167. Kernel API и syscall ABI должны быть разными контрактами.
168. Права выражаются capabilities, ограниченными ресурсом и действием.
169. Принцип минимальных привилегий действует для каждого модуля.
170. Конфигурация отделена от логики и проверяется при загрузке.
171. Безопасные defaults включены до пользовательской настройки.
172. Критическая конфигурация не должна молча заменяться небезопасным значением.
173. Логи содержат component, severity, request_id и source context при необходимости.
174. Не записывай секреты и персональные данные в обычные логи.
175. Метрики имеют единицы, тип агрегации и определённую cardinality.
176. Health сообщает реальное состояние, а не просто факт существования процесса.
177. Readiness и liveness имеют разные значения.
178. Graceful shutdown ограничен временем и освобождает принадлежащие ресурсы.
179. Некритичная функция может деградировать только с задокументированным fallback.

196. Проверяй вход до дорогостоящего выделения или копирования.
197. Любой размер проверяй до сложения и умножения.
198. Любой индекс проверяй до доступа к элементу.
199. Любое смещение проверяй на overflow и границы источника.
200. Каждый цикл ожидания имеет timeout или формально доказанную остановку.

651. Сложная инженерия допустима, когда сложна сама задача.
652. Смелость экспериментировать сочетается с безопасной изоляцией эксперимента.
653. Не бойся пересмотреть решение при новых доказательствах.
654. Не защищай архитектуру только потому, что сам её создал.
655. Признавай чужой вклад и сохраняй его авторство.
656. Делись знаниями в форме, которую можно проверить и применить.
657. Проси помощи до того, как риск станет критическим.
658. Предлагай помощь без присвоения чужой автономии.
659. Сохраняй любопытство, но проверяй предположения практикой.
660. Завершай то, что действительно важно, прежде чем расширять горизонт.

### Шесть итоговых заповедей

**661. Ясность прежде украшения:** пусть каждый элемент Reaper раскрывает намерение.
**662. Контракт прежде обещания:** объявляй готовым только то, что проверено.
**663. Безопасность прежде удобства:** полномочия, память и эффекты остаются явными.
**664. Человек прежде метрики:** код и процессы должны сохранять человеческое достоинство.
**665. Завершение прежде бесконечного расширения:** доводи важное до работающего результата.
**666. Создавай с достоинством:** пиши так, чтобы будущий читатель мог понять, проверить и продолжить твою работу.

## Практический профиль Reaper

### Подтверждённый пример текущего синтаксиса

Следующий пример использует уже существующий стиль `.rpr` и оператор `::`. Он демонстрирует именование, линейный поток, небольшие функции и прозрачные промежуточные значения.

```reaper
craft double_value(value) {
    yield value * 2
}

craft is_large(value) {
    yield value >= 6
}

craft add_values(total, value) {
    yield total + value
}

make source_values := [1, 2, 3, 4, 5]
make result := source_values :: map(double_value) :: keep(is_large) :: fold(0, add_values)
emit "result = " ++ text(result)
```

### Не выдавать проектируемый синтаксис за текущий

Ниже перечислены области, которые могут быть целями языка, но требуют отдельной проверки feature matrix, grammar, compiler и conformance tests: полноценные декларации модулей/типов/trait, `Result<T, E>` как стандартный тип языка, `?`-propagation, ownership/borrowing checker, effect annotations, `->` return types, async/await, прямой native ELF emitter и complete HIR/MIR/LIR backend. До реализации примеры с такими конструкциями помечаются `TARGET / PROPOSAL`.

### Применение к существующему репозиторию

- `.rpr` — основной авторский формат языковой логики и self-hosted компонентов по мере прохождения parity gates.
- Python reference runtime сохраняется как текущая совместимостная реализация и oracle; это не повод писать новые системные реализации DAK на Python.
- Native C17 track остаётся отдельной низкоуровневой реализацией, пока не достигнет подтверждённой функциональной эквивалентности.
- Studio, LSP и DAP используют общие lexer/parser/diagnostic contracts и не объявляют неподдерживаемые возможности.
- Любое расширение языка проходит grammar fixtures, positive/negative tests, stable Span diagnostics, IR validation и migration notes.

## Проверка соблюдения Кодекса

Кодекс внедряется через review checklist, а не через субъективные оценки автора. Для каждого изменения проверяются: ясность имён; действительность синтаксиса; контракт данных; пределы ресурсов; эффекты и capabilities; диагностики и source locations; positive/negative tests; parity соответствующего backend; документация; зрелость feature status; влияние на соседние репозитории и контракты.

Правило считается обязательным только в своей области применимости. Например, naming rule не должен ухудшать ABI, readability rule не должен скрывать critical path, а human-layer rule не отменяет точную диагностику опасного состояния. При конфликте приоритет таков: **корректность и безопасность → контракт и совместимость → ясность → эстетика**.
